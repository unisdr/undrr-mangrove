# Bound rich text alpha

The optional rich TEXT capability accepts source COLOR alpha from0 through1, including fully transparent runs. Omitted `a` retains1. Every imported source/native mode must resolve finite in-range RGB and alpha before target or style writes. No opaque paint or nearest palette substitute replaces an authored translucent run.

[Figma Paint documentation](https://developers.figma.com/docs/plugins/api/Paint/) defines SolidPaint color as RGB and its separate paint opacity as0..1, with a color variable binding. The documented [`setBoundVariableForPaint` helper](https://developers.figma.com/docs/plugins/api/figma-variables/) attaches the COLOR role; the prepared paint receives the resolved RGBA alpha as `opacity`. The complete returned native paint must remain a valid SOLID with the expected variable alias and the requested alpha or its exact Float32 representation. A different finite alpha refuses; there is no epsilon tolerance. Range fill setters apply those prepared paints after font and ownership preflight. Node-wide opacity is not changed.

The normal full plugin enables this capability. Connector specialization may set `MG_CONNECTOR_RICH_ALPHA` false to restore opaque-only validation and paint construction. Existing opaque ownership ledger signatures remain byte-identical: their seven fields do not change. A run whose Float32 alpha differs from1 appends that canonical alpha, so opacity changes affect native ownership, deferred-style coalescing and edit preservation. Emitted source and paint values are unchanged. Root's actual isolated native probe read source0.2 as0.20000000298023224 and0.8 as0.800000011920929 in native paints/variables;0 and1 were exact. This is a representation boundary, not a source rounding correction. Values near1 and tiny positive alpha use the same canonical signature decision before and after native readback. All resolved color-mode values already participate in dependency stamps; changes during font loading or after preparation refuse.

The dedicated harness checks opaque ledger parity against the false profile, omitted alpha, explicit0/0.2/0.8/1, mixed opaque/transparent/translucent ranges, range edits and repeats. Invalid alpha in a nonselected source mode, malformed or finite-but-wrong native bound paints, manually changed range alpha and asynchronous color dependency changes refuse without scene writes. The actual production builder runs a mixed rich component in all five source modes, retains supported consumer edits, proves two nonempty zero-create repeats including paints, range styles, links and ownership ledgers, and refuses a native invalid-alpha role before scene/style/image writes.

These offline API fixtures do not render compositing, prove actual native alias alpha across live mode changes, or establish consumer pixels. The separate isolated native readback probe proves the numerical representation for four alpha values, not full rich builder or consumer acceptance. Existing mode-dependent alpha changes can alter observed ownership signatures and need a separate native mode-switch/migration rehearsal. Unexpected native range setter failures after writing starts retain the existing partial-write behavior; no rollback guarantee is introduced. StatsCard's alpha0.8 linked negative summary depends on this capability. Its fonts, numeric OpenType features, native pixels and full component acceptance remain separate gates.

Compiler source validation and opt-in pruning have separate root-owned tests. No compiled rich build is accepted merely because a source fixture passed: the unchanged50,000-character transport ceiling still applies. Normal DTOs, published libraries and canonical scene identities are unaffected by this capability task.

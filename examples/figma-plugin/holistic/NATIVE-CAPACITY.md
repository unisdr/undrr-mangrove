# Native foundation capacity gate

Source packets preserve source evidence and are deliberately refused by the normal importer. Their successful exporter and mock checks do not establish that the complete source catalogue fits one native collection.

Figma documents a maximum of5,000 variables per collection in [Create and manage variables and collections](https://help.figma.com/hc/en-us/articles/15145852043927-Create-and-manage-variables-and-collections), verified2026-10-06.

The immutable source78 packet at2a7c0c6995a662eb89cb10b5769a5b550386508a contains25,466 foundation variables:23,195 FLOAT,2,266 COLOR and5 STRING. It also has1,288 text styles and96 effect styles. A full one-collection native import is infeasible under the documented limit. The original normal32-family exporter and published25-family pilot are separate; this observation does not change those canonical identities or their existing publication evidence.

The archived initial Cookie Consent22-preset candidate introduced12,697 helper variables. Its source anatomy is under correction and reduction; that historical count is not the final candidate capacity. The staged Topic/Index8-family/50-preset document contains5,236 variables including its dependencies. These are source models with passing bounded offline checks, not accepted complete native imports.

A read-only source78 diagnostic found20,671 component FLOAT helpers with equal values across modes and2,418 with differing values. Equal values alone do not justify merging semantic roles. A tree/style/alias string-reference diagnostic identified16,275 helper FLOAT roles referenced only by recorded allocation fields; hypothetical removal would still leave9,191 variables. That diagnostic is not a validated schema projection, authorisation to remove bindings or native feasibility proof.

The next reviewed native design must distinguish actual maintenance tokens from construction-time captured allocations. Options include source-proven semantic reuse, explicit selected-source-mode allocation specialisation with rebuild semantics, and deliberate helper collection partitioning. The source expressions, aliases, stable identities, complete dependency closure, collection capacity, exact per-collection modes, source drift guards, imported style bindings, edited-instance ownership and repeated builds must remain verified. Arbitrary equality-based deduplication or silent loss of theme bindings is not accepted.

No architecture change is implemented by this document. Full native builders, source font/glyph/pixel fidelity, library integration, selective publication and linked consumer restoration remain open. Canonical, consumer and recovery files are unchanged by this read-only audit.

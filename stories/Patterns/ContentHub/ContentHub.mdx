# Content hubs

> **Note:** A Storybook exploration for [#1112](https://github.com/unisdr/undrr-mangrove/issues/1112), not a published component or a new CMS content type. Review against the [component checklist](https://github.com/unisdr/undrr-mangrove/blob/main/docs/REVIEW-CHECKLIST.md).

A content hub gives a substantial group of pages a shared identity and a reliable
route between sections. Breadcrumbs explain ancestry; hub navigation makes sibling
content discoverable without a return trip to the landing page. Its identity and
section links come from [Hub header](?path=/docs/example-hub-header--docs);
landing pages, including the topic page a hub usually grows out of, are in
[Landing page patterns](?path=/docs/example-landing-pages--docs).

These examples use illustrative Sendai Framework Monitor content. They are not
reporting instructions or a proposed final site map. Internal links navigate within
the example; the header, global menu and reporting-platform links leave the demo.

## Landing page, hub or microsite

Three landing page shapes are drawn out separately in
[Landing page patterns](?path=/docs/example-landing-pages--docs), including the
topic page that is the usual precursor to a hub.

| Pattern      | Its job                                                 | Navigation emphasis                               |
| ------------ | ------------------------------------------------------- | ------------------------------------------------- |
| Landing page | Introduce a subject and direct people to useful content | Parent navigation and grouped routes              |
| Content hub  | Support repeated movement across related pages          | Shared resource name and section links            |
| Microsite    | Support a more distinct experience or subbrand          | Its own navigation with a clear parent connection |

Publishing is a separate choice. Drupal, a static build or another application can
support these experiences. A hub can also link to a tool with its own task-oriented
navigation without adopting that tool's interface.

## Hub home

A stable resource name and short set of section links establish a place within the
parent site. The home page is the most expressive page in the hub: a split hero
carries the title, and the routes and supporting band sit below it.

Note what does not change. The identity row above the hero is the same height and
the same treatment it has on every other page in this set. That is what lets the
hero be expressive here without costing the reader their sense of where they are.

## Hub detail

Try moving from Reporting to How to report, then to another section. Reporting stays
active on descendants, while the page heading and breadcrumbs identify the exact page.
These are ordinary navigation links, not controls for tab panels.

<Canvas of={Stories.HubDetail} />

<Controls of={Stories.HubDetail} />

Every example sits under the standard UNDRR chrome: the `PageHeader` black bar with
the UNDRR logo and language access, then the `MegaMenu` global navigation strip. The
hub identity and section links begin below that, so the examples show the real
vertical budget a hub has to work with rather than an idealized one.

A compact or focused brand header is out of scope for version one. Reworking the
parent masthead is expensive in Drupal templating and would have to hold for
PreventionWeb and the other sub-brands as well. The most that is likely worth
considering later is suppressing the global navigation strip on hub pages, and even
that needs a case made for it. Version one keeps the parent chrome exactly as the
rest of the site renders it.

Use the locale toolbar for Arabic and resize the canvas for mobile. The section
strip scrolls horizontally, keeps ordinary keyboard link navigation and indicates
the current section. The theme toolbar applies Mangrove's shared tokens.

This story is also the argument that the strip is not a tab set: its active item

A dense reference section may benefit from a scoped sibling rail. That remains a
valid alternative: avoid adding both a full section rail and a full in-page rail
without a clear need. A labelled mobile Sections disclosure is another option to
compare when the section strip grows long.

## Variations

Alternatives worth comparing before any of this is settled. Each changes one
thing about the examples above.

### A detached header

The header shares the banner's surface by default, so the two read as one block.
`headerSurface: "detached"` is the opt-out: the navigation bar returns to the
page background and the banner keeps its own colour, so they read as separate
blocks. They stay separate containers either way — which is what keeps the
navigation's contrast predictable.

<Canvas of={Stories.HubDetailDetachedHeader} />

### The same page with a video hero

The comparison worth making, and the reason it is a video. Here the hub header
stays `compact` and a `Hero` block sits below it, the way body content would.

If the page hero carried the same photograph, this example and the one above
would look almost identical — the banner was built to resemble a hero, and
`mg-hero--split` sets `aspect-ratio: unset`, so both are content-height driven.
A screenshot would show you nothing. **What actually differs is capability.**
`Hero` accepts `media.type` of `image`, `video` or `html`, plus immersive and
tone variants. The hub header's banner accepts an image. That is the price of
making it chrome, and it is easier to judge when you can see it.

<Canvas of={Stories.HubDetailWithVideoHero} />

So the choice is editorial rather than visual:

- **Who configures the hero?** If the banner is chrome, hub pages get their hero
  from the hub rather than from the page body — consistent by construction, but
  an editor's knowledge of heroes elsewhere stops transferring.
- **What is a hub page's hero allowed to be?** A chrome-owned banner supports
  what the hub header supports, today and whenever `Hero` grows something new.
  This page could not exist under that model without extending the banner too.

Flip `heroSource` on any story to compare the two directly, and `pageHeroMedia`
to see the same page with a photograph instead.

### Icon routes

`routeCards` swaps the vertical cards for icon cards, which is how undrr.org
already presents "what would you like to do" routes on the live Monitor pages.
The destinations are identical; only the presentation changes. IconCard ships
column-only, so the horizontal arrangement here is a story-local override rather
than a component variant.

## Design decisions

The identity row and section links come from
[Hub header](?path=/docs/example-hub-header--docs), which owns them for every
page type and adds the banner on pages that want it.

> **Implementation note (for contributors):** the rest of this section records why the pattern looks the way it does. Consumers reviewing the examples above do not need it. The fuller [information architecture brief](https://github.com/unisdr/undrr-mangrove/blob/950f2f5695ff253eb6a447362d188e0de35d0957/docs/design/content-hubs.md) carries the research behind it, including alternative mobile and deep-section sketches and the questions still worth testing.

### Why the section strip does not look like tabs

The strip is a row of ordinary page links carrying `aria-current`. It previously
marked the active item with a 3px bottom border and a tinted fill, which is tab
language — and, as it turns out, is also how `Tab`, the MegaMenu topbar and
`OnThisPageNav` all mark their active item. A bottom border in this library says
"a horizontal strip of something is active"; it does not say what kind of
navigation you are looking at.

So the active item here is marked the other way round. It stops looking like a
link: near-black instead of interactive blue, bold, and preceded by a short
leading rule. That leading rule is an existing Mangrove idiom for "the
destination you are on" — `mg-mega-content__section-list-link--active` and the
On this page rail below both use one. Three signals, so the state never rests on
colour alone, and the marker is a border rather than a background so it survives
forced-colors mode.

The hub name shares the row with the links rather than sitting above them. A
named lead-in followed by links reads as navigation within a named resource; tab
sets do not carry a title inside the bar.

Reusing the MegaMenu topbar's classes was considered and rejected. Its
`--active` modifier is the dropdown trigger and carries the same 3px underline,
it sets `pointer-events: none` on its items below tablet so the sidebar can own
mobile, and its `role="menubar"`/`role="menuitem"` markup would collapse these
page links into a single tab stop. Taking only its CSS would leave a lookalike
fork held together by coincidence. What is reused instead is the `Tab` rail's
overflow _mechanics_ — edge fades, scroll padding, hidden scrollbar, the
forced-colors fallback — without its indicator.

### Hub identity and page heroes

Identity is chrome, not a title. The hub name is fixed at 1.125rem in near-black
and the identity row is the same height on every hub page. That invariance is
the mechanism: something that never changes size or position stops being read as
a heading, so it does not compete with the page's own `h1`.

Turn on the `withHero` control to see the case this was designed for. It uses
the split hero at 2/3, matching how undrr.org presents these pages today. The
hero sits below identity, keeps its full bleed, and carries the `h1` itself — the intro block does not render a second one. The
hero's label slot is deliberately left empty: putting the hub name there would
duplicate identity a few pixels below itself, and putting the section name there
would give the "which section am I in" signal two homes that can drift apart.

The On this page links use the shipped `TableOfContents` component rather than a
bespoke rail.

One judgement worth revisiting: the live Monitor pages put the parent name in
the hero's label slot, because there is no persistent identity row to carry it.
Here there is one, directly above, so the label is left empty rather than
printing the hub name twice within a few pixels.

Identity is never merged into the hero and never suppressed by it. Merging fails
because `mg-hero` forces white text over an editor-chosen photograph, sizes its
label smaller than the name needs, and is absent from most hub pages — so
identity would move around, destroying the persistence that is the point of a
hub. Suppressing fails because someone arriving from search would get no
identity and no lateral navigation. Do not use `size="immersive"` inside a hub:
at `clamp(496px, 62vw, 688px)` it pushes the section links off the first screen.

Breadcrumbs sit above the identity row when they appear, matching how the live
Monitor pages order them. They do not appear on most hub pages. On the hub home
the trail's last crumb repeats the hub name a few pixels below it; on a section
page and a first-level detail page it repeats the active section link and the
page heading. It is shown where it says something nothing else does: on a page
deep enough to have an intermediate parent the section strip cannot show, and on
the hub's parent landing page, which has no hub navigation at all.

The cost of hiding it is the route up to the hub's parent landing page, which
nothing else offers — the hub name links to the hub home and the logo links to
UNDRR. Whether that matters depends on whether a given hub has a meaningful
parent page, so this is a rule to test rather than a settled default.

## Composition and possible components

| Already available                               | Explored here                                                              |
| ----------------------------------------------- | -------------------------------------------------------------------------- |
| Vertical cards for grouped routes               | Persistent hub identity and section navigation                             |
| Soft CTA for a route into the reporting tool    | Hub identity sitting below the standard UNDRR header and global navigation |
| Breadcrumb styling, typography and theme tokens | Page hierarchy, optional contents links and responsive placement           |

The prototype uses native breadcrumb links with existing styles, plus VerticalCard
and TextCta. Its `mg-hub-example` layout styles load only with these stories. It adds
no production exports, hydration API or distributed CSS classes, so existing pages
and components retain their behaviour. A small hub identity/navigation component
could graduate from this exploration after testing real labels and page depth.

The hash routing is demonstration code. A production site should supply canonical
page URLs, current-page and active-ancestor state, and its own rendering or routing.
Use distinct navigation labels and `aria-current="page"` for an exact current page;
the prototype uses `aria-current="location"` for its active ancestor section.

## Questions for the next iteration

- Can someone entering on a detail page identify the resource and reach a sibling section?
- With the full UNDRR header and mega menu above it, does the hub's own navigation still read as a distinct place?
- When does a section need a sibling rail or mobile disclosure rather than a scrolling strip?
- Which pages are long enough to benefit from On this page links?
- Can shared content belong to several collections without duplicating its canonical page?

The [GOV.UK service navigation pattern](https://design-system.service.gov.uk/patterns/navigate-a-service/)
provides a useful reference for separating parent identity from local navigation.
Its [current-page and active-section states](https://design-system.service.gov.uk/components/service-navigation/)
help distinguish a section landing page from its descendants. This is an analogy for
content hubs, not a requirement to copy a transactional service header.

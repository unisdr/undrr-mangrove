# Newsletter promotion

A composition of existing Mangrove typography, utility classes and form controls,
not a new signup component or service adapter. Explores [web-backlog #2412](https://gitlab.com/undrr/web-backlog/-/work_items/2412).

Copy, cadence and choices here are illustrative. The form examples simulate a
response locally: no address is stored or sent, and no subscription is created.
Use the locale and theme toolbars, and resize the canvas to compare layouts.

## Validation and confirmation

Submit an empty or invalid address to see validation, then a sample address to see
the simulated confirmation. Focus moves to the confirmation heading and returns
to the email field when starting again.

## What belongs where

| Mangrove pattern                            | Site and service integration                                        |
| ------------------------------------------- | ------------------------------------------------------------------- |
| Spacing, responsive layout and theme tokens | Article placement and editorial targeting                           |
| Labels, grouped choices and focus treatment | Copy, options, cadence and consent requirements                     |
| Validation and feedback presentation        | Server validation, submission, abuse prevention and provider errors |
| Demonstrations of confirmation states       | Whether signup completes immediately or requires email confirmation |

Use native form markup styled by Mangrove when integrating with Drupal. Let the
site supply its real action, field names, hidden fields and submission behaviour.
For provider-hosted forms, link to the signup page or use an appropriately styled
integration. Do not copy the simulated submission handler into production.

The compact example uses a native input inside FormAction. The preferences example
uses TextInput, FormGroup and Checkbox. Buttons are native submit buttons with the
existing Mangrove button classes. The promotional surface uses utility colours and
shared spacing/radius tokens; it introduces no production CSS or component API.

A production implementation should verify success and failure with its real
service, expose any required privacy information, and test keyboard use, screen
reader announcements, RTL, mobile layout and axe checks on the integrated page.

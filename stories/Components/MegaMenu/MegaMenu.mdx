## Usage

```jsx
import { MegaMenu } from '@components';

// Default (no logo)
<MegaMenu sections={menuItems} />

// Branded variant (with logo)
<MegaMenu
  sections={menuItems}
  logoSrc="https://assets.undrr.org/logos/pw/pw-logo.svg"
  logoAlt="PreventionWeb"
/>
```

### Multilingual sites and language-prefixed logo links

Pass the language-prefixed root path to `logoHref` (for example, `"/ar/"` for Arabic). In Drupal, output this from Twig into the `data-mg-mega-menu-logo-href` attribute:

```html
<div
  data-mg-mega-menu
  data-mg-mega-menu-logo-src="https://assets.undrr.org/logos/pw/pw-logo.svg"
  data-mg-mega-menu-logo-alt="PreventionWeb"
  data-mg-mega-menu-logo-href="/ar/"
></div>
```

`logoHref` defaults to `'/'`. If logo asset attributes are absent, the Drupal
wrapper resolves `logoSrc` and `logoAlt` from body class; it does not infer
`logoHref`, so pass language-prefixed roots explicitly.

### Banner HTML trust contract

`bannerDescription` accepts caller-sanitised HTML in desktop banners,
no-items panels and the mobile sidebar. Sanitise it when building `sections`
from CMS/API data, whether passed as a prop or through `data-sections`.
Drupal's filtered text formats can provide this boundary; otherwise use a
sanitiser such as [DOMPurify](https://github.com/cure53/DOMPurify):

```js
import DOMPurify from 'dompurify';

const sections = apiSections.map(section => ({
  ...section,
  bannerDescription: DOMPurify.sanitize(section.bannerDescription),
}));
```

Mangrove does not sanitise this field. The desktop check for `<` selects a
text wrapper or HTML rendering; it is not a filter. `bannerHeading` is plain text.

## Design principles

The desktop menu follows the
[WAI-ARIA Authoring Practices disclosure navigation pattern](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/examples/disclosure-navigation/).
This section records what that means here and why, so changes can be judged
against a reference rather than against the last bug report.

### Why disclosure, not a menu

ARIA `menu` and `menubar` roles describe application menus, such as a desktop
app's File menu. They switch screen readers into a mode where only arrow keys
move, which site visitors do not expect. The APG
[menubar example](https://www.w3.org/WAI/ARIA/apg/patterns/menubar/examples/menubar-navigation/)
itself warns that it is unnecessarily complex for typical site navigation and
points to disclosure instead, and practitioners agree
([Adrian Roselli](https://adrianroselli.com/2017/10/dont-use-aria-menu-roles-for-site-nav.html),
[Inclusive Components](https://inclusive-components.design/menus-menu-buttons/)).
So the navigation is a list of buttons and links, and each button shows or
hides one panel.

### Rules

- **Open on activation only.** A top-level button opens and closes its panel
  on click, Enter or Space, the same for every input. Panels never open on
  focus or hover. The
  [W3C fly-out menu tutorial](https://www.w3.org/WAI/tutorials/menus/flyout/)
  says submenus should not open when tabbing, and opening on hover makes a
  click on an already-open panel ambiguous. Hovering a top-level item still
  shows a light tint and a faint underline bar, so it reads as clickable;
  it changes nothing else.
- **Show what a click will do.** Items that open a panel carry a down
  chevron that turns over when the panel is open; items that go straight to
  a page carry none. The chevron is always shown, not only on hover, so
  keyboard and touch users get the same hint. It is decorative
  (`aria-hidden`), because `aria-expanded` already tells assistive technology. GOV.UK reached the same model
  after usability rounds and an A/B test
  ([GOV.UK menu bar](https://insidegovuk.blog.gov.uk/2021/11/11/launching-gov-uks-new-menu-bar)),
  as did the [Department for Education](https://design-histories.education.gov.uk/get-into-teaching/designing-dropdown-navigation).
- **A trigger is either a button or a link, never both.** A section with a
  panel renders a button with `aria-expanded` and `aria-controls`; its landing
  page (`bannerButton.url`) is offered inside the panel. A section without a
  panel renders a plain link. A link that also expands leaves Enter able to do
  only one of the two, and `aria-expanded` on a link misleads
  ([Roselli](https://adrianroselli.com/2019/06/link-disclosure-widget-navigation.html)).
- **Choosing a category is also a disclosure.** In two-column panels,
  categories are buttons that show their destinations. Focus alone never
  switches them, so Tab moves from a chosen category to its destinations, and a
  screen reader announces which category is expanded. Hovering a category
  still previews it for pointer users; that changes nothing for keyboard or
  screen-reader users. Each category's own page leads its destinations.
- **Tab reaches everything; arrow keys only help.** Tab and Shift+Tab follow
  document order. Arrow keys, Home and End are optional shortcuts, as APG
  describes: screen readers in reading mode use arrows themselves, so no
  destination may depend on them.
- **Easy to dismiss.** Escape closes the panel and returns focus to its
  button, focus moving out of the navigation closes it, and so does a click
  outside. The pointer leaving does not, since the visitor opened it on
  purpose. This also meets
  [WCAG 1.4.13 Content on Hover or Focus](https://www.w3.org/WAI/WCAG22/Understanding/content-on-hover-or-focus.html).

- **On narrow screens, the menu is a modal dialog.** Below 900px the drawer
  follows the
  [APG modal dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/):
  it is labelled, keeps focus inside, closes on Escape and returns focus to
  whatever opened it. The page behind does not scroll, and a swipe past the
  end of a long list stays in the drawer (`overscroll-behavior: contain`).
  Nested groups open on the same surface; Back restores the scroll position
  and focus on the group the visitor came from.
- **Each destination has one predictable home.** Navigation only helps when a
  visitor can guess which category holds what they want. List a destination
  once, under the category a visitor would look in, and name categories after
  what they contain. Repeating a link under unrelated categories, or burying
  it in a long list of a different kind of content, makes visitors scan
  everything
  ([Nielsen Norman Group on mega menus](https://www.nngroup.com/articles/mega-menus-work-well/)).
  The component cannot enforce this; it belongs to each site's information
  architecture. The stories model it: practical guidance has its own category
  instead of repeating under publication types.

### Evidence and limits

The pattern choice rests mostly on expert consensus and the GOV.UK testing
above, not on research with UNDRR audiences. APG examples are not tested with
every screen reader. Some screen-reader users prefer menubar-style arrow
navigation for large menus (see the comments on Roselli's 2017 post); the
arrow shortcuts here offer that without changing the semantics.

What has been checked, in Jest and in real Chromium and WebKit
(`yarn test:megamenu-keyboard-browser`, `yarn test:megamenu-mobile-browser`):

- Tab and Shift+Tab reach every desktop destination from a fresh load and
  after pointer navigation and browser Back, and ArrowDown on a top-level
  button opens the panel rather than scrolling the page. Arrow keys still
  scroll the page when focus is on the page itself, as browsers do; that is
  the likely cause of the page scroll seen in the
  [#1499](https://github.com/unisdr/undrr-mangrove/issues/1499) trial.
- On a phone-sized viewport, a long list scrolls inside the drawer, the page
  behind stays put, the last entry is reachable, and Back and reopening
  restore the expected position. Chromium uses a synthetic touch swipe and
  WebKit the scroll wheel.

Still to verify with people, devices and assistive technology: a physical
phone and tablet (including tablets 900px or wider), NVDA, JAWS and VoiceOver
with the two-column panels, voice control, whether visitors miss
hover-to-open, and whether visitors find destinations in each site's real
content structure. Treat any discovery difficulty seen so far as a research
question, not a pass or a failure.

## Accessibility

### Keyboard navigation

Desktop, following the [design principles](#design-principles):

- **Tab / Shift+Tab** move through top-level items and, when a panel is open,
  through its controls in document order. Every destination is reachable this
  way.
- **Enter / Space** on a top-level button opens or closes its panel. On a
  category button they show that category's destinations, which Tab reaches
  next.
- **← / →** move between top-level items, mirrored in RTL; **Home / End** jump
  to the first or last. **↓** on a top-level button opens its panel and moves
  into it.
- Inside a panel, **↓ / ↑** step through links and controls and **Home / End**
  jump to the first or last; **↑** from the first returns to the panel's
  button. These are shortcuts only, and they leave form fields alone.
- **Escape** closes the panel and returns focus to its button. Moving focus
  out of the navigation, or clicking outside it, also closes the panel.
  Inactive panels are inert and hidden from assistive technology.
- Mobile dialogs contain Tab focus; arrows retain native behaviour. Entering a
  level focuses its heading; Back restores the previous row and scroll position.
  See [mobile navigation](#mobile-progressive-navigation).

### ARIA attributes

The root is a labelled `<nav>` containing a plain list, without `menubar`,
`menu` or `menuitem` roles. Top-level buttons expose `aria-expanded` and
`aria-controls` for their panel; sections without a panel are plain links.
Each panel is a labelled region with section-specific category and submenu
landmarks. Category buttons expose `aria-expanded` and control the
destinations list, which is named after the chosen category.

The mobile opener exposes `aria-expanded`, `aria-controls` and
`aria-haspopup="dialog"`. The dialog is labelled by its current-level heading;
its links and drill-in buttons use native semantics. A branded logo's accessible
name comes from `logoAlt`, falling back to “Home”.

### Find links inside navigation

Set `enableFilter` to search **all menu destinations**, regardless of the
section used to open the finder. The site's Search navigation item is unchanged.

**Desktop:** panels with a left introduction/categories column show **Find in
menu** in a fixed footer. It opens a native modal with a focused input. Results
scroll independently of the input, icon-only Close button and site-search footer.
Close, Escape or a backdrop click restores the footer button while preserving the
underlying category and scroll position. Clear stays in the dialog. Closing the
parent, switching to mobile, disabling filtering or removing the utility clears
the finder; it does not reopen automatically. If the utility disappears, focus
returns to the surviving top-level control.

**Mobile:** the drawer input searches across sections. Clearing restores the
current drill-down level. Results scroll while the input and Close remain visible.

#### Matching and controls

- Every query word must match the title or breadcrumb, in any order. English
  “and” and “&” are optional between other terms: “events news” finds
  “News & Events”. Each matching word is highlighted.
- Ranking favours exact titles and word prefixes, then exact acronyms, then
  inside-word matches and other title matches, before breadcrumb/combined matches. Repeated URLs appear once; each breadcrumb row is one
  link and wraps in RTL or narrow layouts.
- Acronyms match automatically by word initials or internal capitals: “GAR”
  finds “Global Assessment Report” and “PW” finds “PreventionWeb”. Matching is
  case-insensitive and accepts “G-A-R”, “G.A.R.” or “G A R”. English connector
  words such as “for” and “of” may be omitted; numeric years are ignored.
  Whole-label acronyms of at least two letters match titles or individual
  ancestors. Exact acronyms rank above incidental inside-word matches: “RO”
  favours “Regional Offices” over “Conference Proceedings”. Acronym prefixes and invented
  combinations across breadcrumb levels do not match. Displayed names and
  site-search queries stay unchanged.
- If there are no matches, a single word of at least four characters allows
  one insertion, deletion, substitution or adjacent letter swap against whole
  words: “carers” finds “Careers”. Phrases retain non-fuzzy word matching.
- Counts use a hidden live region; no matches show **No matching pages in this
  menu**. `enableSiteSearch` adds an outlined CTA with an RTL-aware arrow,
  preserving the original query. Its default destination is `/search#query=…`;
  provide that page or set `searchUrl`.
- **⌘K / Ctrl K** opens the desktop finder only with focus in its owning panel,
  outside editors. The hint follows the platform. **↑ / ↓** move between input
  and results; **Enter** in the input follows the first result, or site search
  if there are none. Tab retains native control order. IME composition keys do
  not dismiss either surface.

Override `menuFilterLabel`, `filterPlaceholder`, `clearFilterLabel`,
`noFilterResultsLabel`, `filterMatchesCount` (`{count}`), `searchSiteLabel`
(`{query}`) or `closeLabel` through `labels`. See [runtime translations](#runtime-ui-translations).

#### Theme styling and experience principles

The finder reuses Dialog surfaces, native links, 44px targets and shared focus
rings. Themes own surface expression; matches use neutral highlights and bold
text, retained in forced colours. Behaviour is unchanged with `enableFilter={false}`.
See [motion decisions](#motion-decisions) for hover feedback.

| Property                          | Default                     | Purpose                        |
| --------------------------------- | --------------------------- | ------------------------------ |
| `--mg-mega-filter-font-size`      | `--mg-font-size-300` (16px) | Input and destination type     |
| `--mg-mega-filter-meta-font-size` | `--mg-font-size-250` (14px) | Breadcrumbs, labels and status |

Override these on `.mg-mega-wrapper`. The design follows the
[experience principles](?path=/docs/design-decisions-experience-principles--docs);
it has not been validated through user research.

## Server-rendered / CDN usage

MegaMenu supports [layered hydration](https://github.com/PreventionWeb/undrr-mangrove/blob/main/docs/HYDRATION.md). This is a complex-tier component: in most integrations the `sections` prop comes from an API or server-side builder, not from static HTML. The `fromElement` function extracts timing, logo, finder/search options, language, labels and an optional inline JSON sections attribute. Consumer wrappers typically override `sections`.

```html
<div data-mg-mega-menu data-sections='[{"title":"About","items":[...]}]'></div>
```

| Attribute                         | Default     | Description                                                                                                          |
| --------------------------------- | ----------- | -------------------------------------------------------------------------------------------------------------------- |
| `data-delay`                      | —           | Deprecated and ignored since 2.0                                                                                     |
| `data-hover-delay`                | —           | Deprecated and ignored since 2.0                                                                                     |
| `data-sections`                   | —           | JSON array of menu sections (optional; most consumers provide this via API)                                          |
| `data-logo-src`                   | —           | Logo image URL                                                                                                       |
| `data-logo-alt`                   | `''`        | Alt text for the logo image                                                                                          |
| `data-logo-href`                  | `'/'`       | Where the logo links to (e.g., `/ar/` for language-prefixed root)                                                    |
| `data-logo-width`                 | —           | Explicit width for CLS prevention                                                                                    |
| `data-logo-height`                | —           | Explicit height for CLS prevention                                                                                   |
| `data-vf-google-analytics-region` | `mega-menu` | Click-tracker region for the menu; when set to a non-empty value on the host, the nav uses it instead of the default |

> **Drupal note:** The Drupal wrapper reads prefixed attribute names (`data-mg-mega-menu-logo-src`, etc.) and falls back to a `SITE_LOGOS` body-class map when no logo attributes are set. CDN / vanilla HTML consumers use the short `data-logo-*` names above.

```js
import createHydrator from 'https://assets.undrr.org/mangrove/2.6.0/components/hydrate.js';
import MegaMenu, {
  fromElement,
} from 'https://assets.undrr.org/mangrove/2.6.0/components/MegaMenu.js';
createHydrator({
  selector: '[data-mg-mega-menu]',
  component: MegaMenu,
  fromElement,
});
```

See the [hydration guide](https://github.com/PreventionWeb/undrr-mangrove/blob/main/docs/HYDRATION.md) for the full API and integration details.

## Mobile progressive navigation

Below 900px, the nav strip scrolls horizontally with native touch swipes or mouse click-and-drag. Dragging does not open a section. Tap a label to open its
section in the bounded overlay; the hamburger opens all sections. Groups drill into nested
levels on the same surface with labeled Back/Close controls. Section headings
link directly to landing pages; banner content appears inline under links.

Focus and scroll are restored on back/close; Escape and tapping exposed page
close the menu and return focus to opener. The panel uses a translucent blurred
surface with opaque fallback and switches to opaque/no-transition for reduced
motion/transparency, increased contrast, and forced colors.

This is a drop-in update: existing `sections`, logo props, Drupal
attributes, and hydration entry points are unchanged. `labels` also accepts
`backLabel`, `allSectionsLabel`, `closeLabel`, `overviewLabel`,
`toggleMobileNavLabel`; omitted keys use the selected catalogue, then English defaults. Legacy `menuLabel`
is still accepted but no longer displayed.

## Motion decisions

Follow [Motion and animation](?path=/docs/design-decisions-motion--docs).
Panels open on activation, so there are no pointer intent delays; the
deprecated `hoverDelay` and `delay` props are ignored.

- Destinations, category changes and finder open/close/results update immediately;
  there are no category pulses, panel flashes or staggered links. The public
  `mg-mega-content__right--sliding` class remains a compatibility hook.
- Mobile surfaces and newly entered levels use an 8px logical offset with the
  fast (160ms) duration and standard easing. The backdrop uses a fast opacity
  transition. `@starting-style` supplies entry; unsupported browsers open immediately.
- Finder controls/result rows use reversible fast background-colour transitions
  only for hover-capable devices with no motion preference, outside forced colours.
  Keyboard and touch feedback stay immediate. Shared CTA styles own site-search
  button feedback. Desktop reveals and legacy chevrons use the medium (300ms) token.

Reduced motion and forced colours remove movement without hiding content or
active states. Mobile travel mirrors in RTL. Exit retention reads themed CSS
durations/delays; closing releases focus and scroll immediately and makes retained
content inert. Reopening cancels pending removal. Preference changes leave the
current state usable; hydration and resting theme changes add no incidental motion.

## Analytics

UNDRR sites load a shared GA4 click tracker that names each click after the element's visible text unless `data-vf-analytics-label` is set. MegaMenu sets fixed English labels on its controls so reports do not split by language or record what visitors type: `Mega menu: Open` (hamburger), `Mega menu: Close` (hamburger while open, drawer Close and backdrop), `Mega menu: Back`, `Mega menu: Section` (section buttons in the nav strip and drawer; the section name is not included), `Mega menu: Category` (category buttons in a desktop panel), `Mega menu: Finder` (the ⌘K/Ctrl K finder action), `Mega menu: Filter` (finder and drawer filter inputs, and the finder's label), `Mega menu: Clear filter`, `Mega menu: Close finder` and `Mega menu: Site search` (the site-search link, whose visible text contains the typed query). Navigation links keep their visible text. The site-search link's `href` leaves out the query, because the tracker also reports link URLs; the query is added only while the link is being followed (click or middle-click) and removed straight after, so copying the link gives the search page without the query.

The root `<nav>` gets `data-vf-google-analytics-region="mega-menu"`, so menu clicks are reported separately from the rest of a site header. Set the `analyticsRegion` prop to use another name, or `null`/`''` to inherit an ancestor's region. When hydrating, the menu uses the host's region if the host element has a non-empty `data-vf-google-analytics-region`; an empty value is ignored and the default applies.

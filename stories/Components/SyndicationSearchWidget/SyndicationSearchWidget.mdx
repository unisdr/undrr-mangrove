# UNDRR syndication search widget

The **UNDRR syndication search widget** provides keyword search, faceted
filtering, and list/card/book-card display modes across UNDRR domains.

> **Platform dependency:** This component requires access to the UNDRR search backend via `/search-endpoint`. It includes domain configurations, content type mappings, and taxonomy endpoints specific to the UNDRR platform. It is **not** a general-purpose search component.

> **Future:** A standalone, configurable search component without platform dependencies may be developed separately for broader use cases.

> **Integration note:** Editors placing the widget on UNDRR websites configure it through the UNDRR Search Widget block in Drupal Gutenberg. [Editor configuration](?path=/docs/components-syndicated-search-editor-configuration--docs) covers every block setting, practical configurations, what readers can type and the `field:value` filter syntax with taxonomy term IDs. AI tools can read it as plain text at https://mangrove.undrr.org/llms-search-widget.txt.

## Features

- Keyword search with responsive input and live result updates
- Non-blocking updates keep the page interactive while loading
- Removable filter chips for active filters
- Full ARIA support, keyboard navigation, screen reader announcements
- Mangrove token-based styling
- Inline-start filter drawer on mobile, inline sidebar on desktop
- Custom searchable/multi-select dropdowns (no Chosen.js dependency)

> **Implementation note (for contributors):** The non-blocking search experience is powered by React 19's concurrent rendering features: `useDeferredValue` keeps the search input responsive while results load in the background; `useTransition` marks filter changes as non-urgent to prevent UI blocking.

## Custom filters

`customFilters` are raw Elasticsearch query-string constraints applied

**This example uses:**

  'published_at:[2023-01-01 TO *]', // Content from 2023 onwards
];

## Event listings

The UNDRR index holds `event_start` and `event_end` date fields for `event` and `conference_event` content (`event_end` falls back to the start date, so every event has both). Search API indexes date-only values at 12:00 UTC.

- **Upcoming or past events** use `customFilters` with Elasticsearch date math, so Elasticsearch decides what "today" is and server-rendered results honour it without a baked-in timestamp. Both keep results without `event_end`, such as news in a mixed listing:
  - Upcoming: `(event_end:[now-1d/d TO *] OR (*:* -_exists_:event_end))`
  - Past: `(event_end:[* TO now-1d/d} OR (*:* -_exists_:event_end))`

  The cutoff is `now-1d/d`, the start of yesterday, rather than `now/d`. Date math rounds in UTC, so with `now/d` an event ending today in the Americas would move to "past" in the afternoon there while it is still running; the extra day keeps it upcoming until the day after it ends. The Drupal block's event status setting writes these filters for editors.

- **`defaultSort: 'eventDateAsc'`** (soonest first) or **`'eventDateDesc'`** (latest first) sorts by `event_start`. Results without an event date sort last in both directions, and ties (date-only events share 12:00 UTC) are broken by publish date, newest first, then `nid`, so paging is stable. The sort uses `unmapped_type: 'date'`, so it is safe on an index that doesn't have the field yet.

The Sort dropdown offers the two event date sorts when `defaultSort` is one of them or the widget has encountered one during the current session (for example through a shared URL). Once available, both choices remain available after selecting a different sort or moving between layouts. Ordinary listings that have never used an event sort keep the standard choices, so they don't show sorts that would push every non-event to the end. To limit a listing to a date window, add a `customFilters` range such as `event_start:[2026-01-01 TO 2026-03-31]`.

In list mode without teaser HTML, event results show their event date (a range when the event runs over several days) instead of the publish date.

### Endpoint trust contract

The widget renders HTML from the search response without sanitising it. Result
teasers, and the highlighted title and snippet, go straight into the page as
markup. This is deliberate: Elasticsearch wraps matched terms in `<em>`, and
escaping the response would print those tags instead of emphasising the match.

Point `searchEndpoint` only at a service you trust to return safe HTML. The
default, `https://www.undrr.org/search-endpoint`, is UNDRR's own proxy over the
syndication index. If you point it at your own service — through the
`searchEndpoint` config value or the `data-search-endpoint` attribute — then
whatever that service returns is rendered on your page, and you own what comes
back. Sanitise in the endpoint, not in the widget.

This matters more here than in a component that renders its own site's content.
The widget exists to be embedded on partner sites, so the page carrying the
markup is often not the same organisation as the index behind it.

Nothing from the search box reaches the page as markup: highlights are built
from indexed documents, not from the query, so the query text is not reflected
back.

### Taxonomy endpoint

The country and region, hazard and theme facets get their labels from a
taxonomy API, set by `taxonomyEndpoint` (or `data-taxonomy-endpoint`). The
default is the PreventionWeb v1 taxonomy view:

```
https://www.preventionweb.net/api/v1/taxonomy?vid=prevention_web_regions,hazard,theme&items_per_page=1000&langcode=en
```

The endpoint must return JSON with a `results` array of `{ id, name }` terms,
and it must return **every published term** of the three vocabularies
(`prevention_web_regions`, `hazard`, `theme`). The widget treats a term missing
from the list as unpublished or deleted, so an endpoint that drops terms hides
real filter values. In particular, a `langcode` filter returns only terms
translated into that language: with `langcode=ar` most countries are missing
and would be hidden. If the response is paged (`pager.pages` above 1), the
widget fetches the remaining pages with `page=N`, up to 20 pages; a response
reporting more pages is treated as a failure.

Names are HTML-entity decoded once on load (Drupal's views escape them, so
`Côte d&#039;Ivoire` arrives encoded). One request per endpoint is shared by the
sidebar, the mobile filter drawer and the active filter chips. A successful
response is kept for the rest of the page load; a failed or empty one is
retried the next time one of those components mounts.

Once terms have loaded, values on these three facets that have no matching term
(an unpublished or deleted term still referenced by content) are left out of
the dropdown. A value that is already selected stays visible, labelled with its
raw ID, so it can be removed. Nothing is hidden while terms are loading, if the
request fails, or if it returns no terms (for example a Cloudflare challenge
page instead of JSON). Within one facet, nothing is hidden unless at least one
of its values has a label, so an endpoint that leaves out a whole vocabulary
does not empty that facet.

The hiding applies to facets marked `labelSource: 'taxonomy'` in
`FACET_FIELDS`. If you pass your own `facetFields`, keep that marker on the
country and region, hazard and theme entries.

## Query syntax reference

The search input uses Elasticsearch `query_string` syntax, forwarded directly to the `/search-endpoint` proxy. Drop any of the queries below into the search box on the [Default story](?path=/story/components-syndicated-search--default) to verify behaviour, or use them as a reference when writing `customFilters`.

### Basic queries

| Query                                  | Description       | Expected behaviour                                                      |
| -------------------------------------- | ----------------- | ----------------------------------------------------------------------- |
| `climate change`                       | Simple multi-word | Matches docs with both words (AND), stop words removed, fuzziness added |
| `disaster risk reduction`              | Common phrase     | Stop words "the", "of" etc. removed for consistent matching             |
| `The Draft Articles on the Protection` | With stop words   | Same results as "Draft Articles Protection"                             |

### Exact phrase matching

| Query                       | Description  | Expected behaviour                                         |
| --------------------------- | ------------ | ---------------------------------------------------------- |
| `"climate change"`          | Exact phrase | Matches exact phrase, no fuzziness, no stop word removal   |
| `"Draft Articles"`          | Exact phrase | Finds documents with "Draft Articles" as consecutive words |
| `"disaster risk reduction"` | Exact phrase | Stricter matching than without quotes                      |

### Wildcards and fuzzy

| Query         | Description             | Expected behaviour                         |
| ------------- | ----------------------- | ------------------------------------------ |
| `ris?`        | Single char wildcard    | Matches "risk", "rise", etc.               |
| `red*`        | Multi-char wildcard     | Matches "reduction", "reduce", "red", etc. |
| `evnt~1`      | Fuzzy (edit distance 1) | Matches "event" (typo tolerance)           |
| `earthquke~2` | Fuzzy (edit distance 2) | Matches "earthquake"                       |

### Boolean operators

| Query                    | Description    | Expected behaviour       |
| ------------------------ | -------------- | ------------------------ |
| `flood AND drought`      | AND operator   | Both terms required      |
| `flood OR drought`       | OR operator    | Either term matches      |
| `flood NOT tsunami`      | NOT operator   | Excludes tsunami results |
| `-"Red Cross"`           | Exclude phrase | Excludes exact phrase    |
| `(UNDRR AND "New York")` | Grouped        | Parentheses for grouping |

Operators must be uppercase. Lowercase "and" and "or" are treated as ordinary words and removed as stop words, so `flood or drought` requires both terms. When the widget sets `queryAppend`, the reader's query and the appended query are combined as `(reader query) AND (queryAppend)`, so an OR typed by a reader can't widen the results beyond what `queryAppend` allows.

### Field-specific searches

| Query                        | Description       | Expected behaviour              |
| ---------------------------- | ----------------- | ------------------------------- |
| `title:sendai`               | Search title only | Matches "sendai" in title field |
| `_language:en`               | Language filter   | English content only            |
| `type:landing`               | Content type      | Landing pages only              |
| `type:(news OR publication)` | Multiple types    | News or publications            |

### Date ranges

| Query                                     | Description | Expected behaviour        |
| ----------------------------------------- | ----------- | ------------------------- |
| `published_at:[2023-01-01 TO 2023-12-31]` | Date range  | Content from 2023         |
| `published_at:[2020-01-01 TO *]`          | Open range  | Content from 2020 onwards |
| `published_at:[* TO 2022-12-31]`          | Open range  | Content before 2023       |

### Boosting

| Query                        | Description    | Expected behaviour             |
| ---------------------------- | -------------- | ------------------------------ |
| `history^1.1 review`         | Term boosting  | "history" weighted 1.1x higher |
| `title:sendai^2 body:sendai` | Field boosting | Title matches weighted 2x      |

### Edge cases verified by the query builder

| Query          | Description       | Expected behaviour                      |
| -------------- | ----------------- | --------------------------------------- |
| `a`            | Too short         | Should not trigger search (min 3 chars) |
| `   spaces   ` | Extra whitespace  | Trimmed and searched as `spaces`        |
| `:`            | Special char only | Handled gracefully                      |
| `""`           | Empty quotes      | Handled gracefully                      |

### Query sanitisation (auto-fixed)

These malformed queries are automatically sanitised to prevent Elasticsearch errors:

| Query         | Problem               | Auto-corrected to  |
| ------------- | --------------------- | ------------------ |
| `"local`      | Unclosed quote        | `local`            |
| `local OR `   | Trailing operator     | `local`            |
| `AND climate` | Leading operator      | `climate`          |
| `flood OR`    | Trailing OR           | `flood`            |
| `AND`         | Standalone operator   | (empty, no search) |
| `climate-`    | Trailing special char | `climate`          |

### Integration with Drupal

The component is loaded automatically on pages containing a container with `data-mg-search-widget`:

```html
<div
  data-mg-search-widget
  data-search-endpoint="https://www.undrr.org/search-endpoint"
  data-results-per-page="50"
  data-default-query=""
  data-default-sort="relevance"
  data-show-facets="true"
  data-default-filters='[{"key":"_language","value":"en"}]'
>
  <!-- React SearchWidget mounts here -->
</div>
```

`data-search-endpoint` sets the same value as the `searchEndpoint` config key,
and carries the same responsibility: the widget renders that endpoint's HTML
unsanitised. See [Endpoint trust contract](#endpoint-trust-contract).

On the UNDRR Drupal platform, the `undrr/search-widget` Gutenberg block saves
its own container, marked `data-undrr-search-widget`. That attribute belongs to
the platform, not to this library: a wrapper script in the platform theme finds
those containers, reads their `data-*` attributes and mounts this component
itself. Mangrove never reads `data-undrr-search-widget` (see 1.4.12 below), so
markup outside the platform should keep using `data-mg-search-widget`.
The block's settings and the filter values editors use are documented in
[Editor configuration](?path=/docs/components-syndicated-search-editor-configuration--docs).
Backend notes (relevance scoring, synonyms, the configuration modifier
pattern and library load order) are maintained with the Drupal module in the
platform codebase.

## URL hash

With hash sync on (`enableHashSync`; see the props table), the widget keeps
its state in the URL fragment, so a filtered view can be bookmarked or shared
and the browser's back and forward buttons move between filter states.

```
#query=flood&page=2&sort=newest&f.field_hazard=12&f.field_hazard=34&op.field_hazard=AND&f.type=field_news_type:751
```

| Parameter  | Meaning                                                                                                        |
| ---------- | -------------------------------------------------------------------------------------------------------------- |
| `query`    | Search text                                                                                                    |
| `page`     | Results page, written when above 1                                                                             |
| `sort`     | `relevance`, `newest`, `oldest`, `eventDateAsc` or `eventDateDesc`, written when it differs from `defaultSort` |
| `f.<key>`  | A selected value of the facet `<key>`; repeat the parameter for several values                                 |
| `op.<key>` | `AND` or `OR` for a multi-value facet; written only for `AND`, since `OR` is the default                       |
| `label`    | Replaces the page's `h1` text when the page loads. It is read once and not written back                        |

Rules:

- **Only known facets.** `f.*` and `op.*` keys must be keys of the active
  facet fields (`facetFields`, or the default `FACET_FIELDS`). Anything else
  is ignored, as are invalid `op` and `sort` values, and the URL is tidied to
  the parameters actually applied. Facet keys become Elasticsearch field
  names, so unknown keys never reach the query.
- **The hash replaces the defaults.** If the hash has any valid `f.*`
  parameter, its facets replace `defaultFilters` entirely, including filters a
  host page adds (such as the Drupal block's current language and domain
  detection). With no `f.*` parameters the defaults apply as usual.
- **Defaults keep a clean URL.** Facets are written when their values or AND match mode differ from
  `defaultFilters`; when they do, every selected facet is written, defaults
  included, so the link reproduces the view exactly. A consequence: if a reader
  removes every filter, including the defaults, the URL has no `f.*`
  parameters and reloading brings the defaults back.
- **Clear all returns to the configured baseline.** The reader-facing button restores every `defaultFilters` value, including hidden language/site defaults, clears custom facet selections and match operators, and resets page 1. It preserves the query and sort. Unchanged default groups do not appear as removable chips; a different AND constraint remains visible. Defaults are not access control: explicit `f.*` links still replace them. Use `customFilters` for a scope readers must not remove. Programmatic `actions.clearFacets()` without arguments still empties selections; its optional `{ defaultFilters }` argument requests a baseline reset.
- **Other fragments preserve native navigation.** A skip link (`#main-content`) or table-of-contents anchor keeps its fragment and does not change the current search. Back/Forward restores that anchor entry's same-document search snapshot. The first search edit away from an anchor adds an entry, including typing; later typing replaces the search entry as usual. A same-document widget remount can recover the snapshot. Copying the anchor URL or loading a new document uses configured defaults, because filters are not encoded in an anchor URL. The snapshot is not a shareable search link.
- **Host history state is preserved.** Private snapshots merge into null/plain-object `history.state` without removing unrelated keys. A host-owned primitive, array or other non-record value stays untouched; without a writable snapshot, returning to an anchor falls back to configured defaults. Browser back/forward cache retains same-document snapshots.
- **Reserve search-like anchor names.** IDs exactly `query`, `page`, `sort` or `label`, or beginning with `f.` or `op.`, are interpreted as search parameters. Choose other IDs when hash sync is enabled.
- **Page numbers are bounded.** A `page` beyond Elasticsearch's 10,000-result
  window (for the configured `resultsPerPage`) is ignored, and page 1 is shown.
- **History.** Choosing a filter, a match mode, a sort order or a page adds a
  history entry. Typing a search query updates the current entry instead.
- **Custom facets are not included.** Editor-defined facets (`customFacets`)
  store selections by option position, so a link would select a different
  option after an editor reorders, adds or removes options. They need stable
  option IDs before they can be shared in the URL.

Pages with more than one widget should leave hash sync on for at most one of
them; the Drupal block's `auto` setting does this.

`facetsTarget` and `searchTarget` are matched in the document the widget is mounted in, not the global `document`. On a normal page these are the same document. They differ when the widget renders inside an iframe while its script runs in the parent window, as in a block editor canvas (Drupal's Gutenberg 4 editor, for example): the targets are found in the iframe, next to the widget. The same applies to the widget's other document lookups: the pager's scroll back to the results, the dropdown backdrop, and the mobile filter drawer's scroll lock and Escape key handling. A target that exists only in another document is not found, and the widget falls back to its in-widget layout with a console warning.

## Analytics regions

The widget marks its search form, results and facets with `data-vf-google-analytics-region`: `undrr-search-form`, `undrr-search-results` and `undrr-search-facets`. The shared UNDRR analytics script reports each click with the innermost region around it, so a region set on a section around the widget is never reported for clicks inside it.

When a page has more than one widget, give each its own `analyticsRegionPrefix` (data attribute `data-analytics-region-prefix`). The prefix replaces `undrr-search` in all three names:

```js
const config = { analyticsRegionPrefix: 'collection-related' };
// Regions: collection-related-form, collection-related-results and
// collection-related-facets
```

```html
<div
  data-mg-search-widget
  data-analytics-region-prefix="collection-related"
></div>
```

Without it, nothing changes. A Drupal block wrapper that builds the config itself needs to pass the setting through.

## Results notification

After each completed search the widget calls `onResults({ total, query, page })` and dispatches an `mg-search-widget:results` event with the same `detail`, bubbling from its root. A host uses it to hide a section around a widget that found nothing, or to show the total somewhere else; the event works without React:

```js
document.addEventListener('mg-search-widget:results', event => {
  const section = event.target.closest('section');
  if (section) section.hidden = event.detail.total === 0;
});
```

Until its first results arrive the widget shows its loading skeleton (or the server-rendered results, see [Server-rendered results](#server-rendered-results)); it asks for a search term only when the query is shorter than `minSearchLength` and no filters are set, the one case where it won't search. After that, an empty query that finds nothing says "No results found". When a new search runs with results on screen, the results stay, dimmed, with a small loader in the results header, and retained result links keep their DOM identity and keyboard focus when the response arrives; the skeleton is only for the first load. The results region uses the shared flush indeterminate ProgressBar, with its existing status text and `aria-busy` owning announcements. Skeletons keep stable geometry without shimmer; retained results, the strip and the inline Loader provide refresh feedback without an additional pulsing overlay. Under reduced motion, result fades stop and the shared strip becomes a still dashed pattern; the decorative inline Loader becomes a still complete shape beside visible translated pending text, without adding another live announcement. Forced colours keeps the strip and skeleton outlines visible. Enter, the search button, Clear, and back/forward search at once; only typing waits for `debounceDelay`. A widget with nothing interactive (no search box and no facets, a fixed list of cards) does not announce its total in the live region; every other widget does.

### Motion and loading states

Follow [Motion and animation](?path=/docs/design-decisions-motion--docs). Interaction transitions and the initial results-surface opacity fade use `--mg-motion-duration-fast` and `--mg-motion-easing-standard`, only under `prefers-reduced-motion: no-preference`. The filter drawer uses `--mg-motion-duration-medium`, mirrors inline-start travel in RTL, and appears immediately under reduced motion. Focus moves on opening without waiting for animation; closing unmounts immediately. Legacy pending/visible result classes are retained for consumers, with their hidden start state gated alongside the transition. Typing debounce and other behavioural delays are unchanged. The public legacy `.mg-search__spinner` is a separate compatibility exception, rather than the shared Loader policy, and remains compatible for existing hand-written markup: `--mg-search-spinner-duration` is one revolution (`1s`, three times longer under reduced motion), with system-colour border segments in forced colours. New implementations use shared Loader instead.

Migration: `.mg-search__progress-bar` and `mg-search-progress` are removed. The `.mg-search__progress` positioning wrapper now contains shared ProgressBar markup; consumers overriding the old segment should use ProgressBar properties instead.

These deterministic states use the same results, progress and drawer components without a live search endpoint. Complete, refresh or fail a search to inspect the state changes. Check reduced motion, forced colours and their combination, all themes, and RTL; use a narrow viewport for the filter drawer.

<Canvas of={MotionStories.InitialLoading} meta={MotionStories} />
<Canvas of={MotionStories.RefreshingResults} meta={MotionStories} />
<Canvas of={MotionStories.ResultsEntry} meta={MotionStories} />
<Canvas of={MotionStories.FilterDrawer} meta={MotionStories} />

After paging, the widget scrolls back to its results (instantly under `prefers-reduced-motion`) and moves focus to the results count, or to the results area when the count is hidden, instead of leaving it on a pager button that has been replaced.

## Server-rendered results

A page can render the first results on the server so they show before the widget's JavaScript runs. Without a handoff, mounting empties the container and the page collapses until the client results arrive. To keep the server markup on screen until then:

1. Mark the container with `data-mg-ssr`. The hydration runtime then leaves its content in place instead of clearing it before mounting; React replaces it at its first commit, in the frame that paints the widget.
2. Put the server-rendered results in a child element marked `data-mg-search-ssr`. `fromElement` captures it as `config.ssrResults` before React's first commit.
3. The widget moves that element into its results region (an `aria-busy` slot) before the first paint, so the server results sit where the client results will go, with the search box and facets around them. When the first client results, or an error, commit, the slot and the server markup are removed.

```html
<div data-mg-search-widget data-mg-ssr data-results-per-page="10">
  <div data-mg-search-ssr>
    <!-- the first page of results, rendered by the server -->
  </div>
</div>
```

### Server results markup

Render the server results with the same structure and classes as the widget's own results, so they get the same layout, spacing, borders, containment and block images, and the swap doesn't move anything. In list mode:

```html
<div data-mg-search-ssr>
  <div class="mg-search__results">
    <div class="mg-search__results-header">
      <p class="mg-search__results-count">Showing 1–10 of 245 results</p>
    </div>
    <div
      class="mg-search__results-list"
      role="list"
      aria-label="Search results"
    >
      <div role="listitem">
        <article class="mg-search__result" data-result-type="news">
          <!-- the item's teaser HTML -->
        </article>
      </div>
      <!-- one listitem per result, resultsPerPage of them -->
    </div>
  </div>
</div>
```

- Add the widget's hidden-field classes to the list when teaser fields are hidden (`mg-search--hide-image`, `mg-search--hide-date` and so on, from `buildHiddenFieldClasses(visibleTeaserFields)`).
- In card modes, use `<div class="mg-search__results-grid mg-grid mg-grid__col-N" role="list">` with the card variant classes the widget applies (`mg-card__vc`, plus `mg-card__book` for book cards).
- Render as many results as `resultsPerPage`. Leave out the results header only if `showResultsCount` is off.
- Server results don't fade in, and neither does the first client result set that replaces them.
- `[data-mg-search-ssr]` is itself positioned and isolated, so markup that doesn't use these classes still can't cover the page.

### Custom wrappers

A wrapper that builds the config and calls `createRoot` itself passes the element as `ssrResults`, captured before mounting (React's first commit empties the mount target). Only an `Element` is accepted, not a selector. Each widget needs its own server results element; two widgets must not share one.

If the widget won't search (a query shorter than `minSearchLength` with no filters, from the URL for instance), the server results are removed and the widget asks for input. If keyboard focus was inside the server results when they go, it moves to the results count, or to the results region.

## UI labels

Every user-visible string can be overridden via `labels`. Unspecified keys fall
back to `DEFAULT_LABELS`.

```jsx
<SyndicationSearchWidget
  config={config}
  labels={{
    searchPlaceholder: 'Rechercher…',
    submitSearchText: 'Rechercher',
    noResults: 'Aucun résultat trouvé pour « {query} ».',
    // Dynamic strings use {token} placeholders substituted at render time.
    // Function values enable complex plural forms (Arabic, Russian):
    srResultsFoundPlural: ({ count }) => `${count} résultats trouvés`,
  }}
/>
```

The full list of keys and their English defaults is in `DEFAULT_LABELS` (exported from `SearchContext.jsx`). See the **Translations** stories for complete label sets in Spanish, French, Japanese, Simplified Chinese, Arabic, and Russian.

### Drupal / server-rendered usage

In a Drupal Twig template, supply translated labels via the `data-labels` JSON attribute:

```html
<div
  data-mg-search-widget
  data-search-endpoint="/search-endpoint"
  data-labels='{"searchPlaceholder":"Rechercher…","submitSearchText":"Rechercher","noResults":"Aucun résultat trouvé pour \"{query}\"."}'
></div>
```

`fromElement` parses the JSON and passes it through as the `labels` prop. Unspecified keys fall back to English.

> **Important:** Function-valued labels (needed for Arabic/Russian plural forms)
> cannot be expressed in JSON. Use a custom JS labels object, or accept fallback
> plural strings and handle pluralization server-side.

> **Drupal Twig note:** Use single quotes for the `data-labels` attribute value so that the JSON's double quotes remain unescaped. If any translated string itself contains an apostrophe (common in French), encode it as `’` (the Unicode right single quotation mark) in the JSON, or escape it as `&#39;` in the HTML attribute.

> **RTL layout:** Supplying Arabic labels via `data-labels` or the `labels` prop translates the text content only. The widget's CSS currently uses physical properties and does not flip for right-to-left scripts. RTL layout support is tracked as a separate issue.

### `labels` prop vs `config` prop

`labels` contains UI text only. Search behavior (endpoint, facets, filters,
pagination) belongs in `config`.

## Architecture

> **Implementation note (for contributors):** Uses React 19 concurrent features: `useDeferredValue` keeps input responsive while results load; `useTransition` marks filter changes as non-urgent; `Suspense` provides loading skeletons; Context + `useReducer` manages search state without external dependencies.

### Component structure

```
SyndicationSearchWidget
├── SearchProvider (context)
│   ├── SearchForm (input + button)
│   ├── ActiveFilters (filter chips)
│   ├── SearchResults (with Suspense)
│   │   └── ResultItem (×n)
│   ├── FacetsSidebar (desktop)
│   │   ├── SortOptions (relevance/newest/oldest, event date sorts on event listings)
│   │   ├── FacetSelect (×n, from Elasticsearch aggregations)
│   │   │   └── SelectDropdown (custom Chosen-like component)
│   │   └── CustomFacetSelect (×n, editor-defined)
│   └── MobileFilterDrawer (mobile, <800px)
│       └── FacetsSidebar (reused)
```

### Custom select dropdown

The facet dropdowns use a custom `SelectDropdown` component instead of Chosen.js, with the same core functionality and no external dependencies:

| Feature                 | Description                                 |
| ----------------------- | ------------------------------------------- |
| **Searchable**          | Filter input shown when options > 8         |
| **Multi-select**        | Checkbox indicators, multiple selections    |
| **Single-select**       | Radio indicators, one selection             |
| **Keyboard navigation** | Arrow keys, Enter, Escape                   |
| **Touch-friendly**      | 44px trigger height, 40px option height     |
| **Accessible**          | ARIA listbox pattern, screen reader support |

This works in Drupal, Storybook, and standalone usage without Chosen.js.

### Mobile filter drawer

On screens ≤800px, the sidebar is replaced with a drawer that slides in from the inline start — the left edge in English, the right edge in Arabic:

- Amazon-style slide-in from the inline-start edge, with the shadow cast over the page content
- Click backdrop to close (the inline-end side)
- Sticky header and footer with "View results" button
- Focus trapping for accessibility

UX patterns informed by [Pencil & Paper's mobile filter analysis](https://www.pencilandpaper.io/articles/ux-pattern-analysis-mobile-filters).

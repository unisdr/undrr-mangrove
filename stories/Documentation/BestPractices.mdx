Use these rules to keep integrations maintainable, accessible, and consistent across UNDRR sites.

## Architecture

- Keep domain logic in your app and treat Mangrove as a UI layer.
- Wrap Mangrove components where your product needs local defaults or analytics hooks.
- Preserve semantic HTML structure from Storybook examples so accessibility and syndication assumptions stay valid.
- For server-rendered apps, use `createHydrator` + `fromElement` rather than custom boot code.

## Styling

- Prefer Mangrove tokens (`--mg-*`) over hard-coded colors, spacing, and z-index values.
- Keep overrides scoped and minimal; avoid broad global resets that can break component states.
- Use `mg-` classnames as authored; avoid renaming or flattening BEM structures.
- Pin production sites to a versioned CDN URL, not `latest`.
- Decide the page root's `overflow-x` yourself. Mangrove's full-bleed components are sized in `100vw`, which counts the vertical scrollbar, so a scrolling page gains ~8px of horizontal scroll. `overflow-x: clip` on both `html` and `body` removes it, at the cost of making anything wider than the page unreachable — check your wide tables first. See [page-level setup](?path=/docs/components-fullwidth--docs#page-level-setup).

## Progressive enhancement

- Baseline first: ensure content and key actions work without JavaScript.
- Enhance interactions after hydration; do not make JS-only controls the sole path for core tasks.
- Keep native controls where practical (form fields, focus order, keyboard behavior).
- In hydration code, keep failure fallback behavior so server HTML still renders on client errors.

## Quality checks

- Run tests and linting before opening a PR.
- For CSS-heavy changes, verify in a real browser (not only jsdom tests).
- Update component changelog sections in MDX when behavior, API, or visuals change.
- If structure or utility usage changes, update AI manifest docs (`scripts/ai-manifest/`).

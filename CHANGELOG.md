# Changelog

Detailed change records live in two places:

- **Project releases**: [GitHub Releases](https://github.com/unisdr/undrr-mangrove/releases) — library-wide version history.
- **Component changelogs**: Each component's MDX file has a `## Changelog` section with per-component version history. Browse them in [Storybook](https://mangrove.undrr.org/) or in the `stories/` directory.

For the changelog format specification, see the [component contribution guide](https://mangrove.undrr.org/?path=/docs/contributing-component-standards--docs#changelog-format).

This file collects only cross-cutting library-wide notes that don't fit either location above (e.g. repo-wide build / tooling / policy changes).

## Unreleased

_Notable cross-cutting changes between releases land here. Per-component changes belong in the component's MDX changelog._

- **The published package stops advertising a root entry point.** This is a **consumer-visible change to the shape of the npm package**, and nothing that works today breaks. `scripts/assemble-npm-package.mjs` wrote `main: "dist/index.js"` into the generated `package.json`, naming a file the tarball has never contained: `files` excludes `dist/`, and `npm pack` of `2.0.0-rc.2` (`next`) and `1.8.2` (`latest`) ships zero files under `dist/` or `src/`. So `import … from '@undrr/undrr-mangrove'` has failed with `ERR_MODULE_NOT_FOUND` on every version ever published, and the `main` was a promise to a consumer that no release kept. 2.0.0 removes it. Read in release notes: **if a root import ever worked for you, it did not — you were resolving something else.** The working surface is unchanged and is what it always was, the per-directory subpaths: `@undrr/undrr-mangrove/components/IconCard.js`, `…/css/style.css`, `…/scss/…`, `…/js/…`, `…/fonts/…`, `…/error-pages/…`. Making the root work instead was considered and rejected: the only cheap way is a barrel over `components/`, and `components/ShowMore.js` and `components/Tab.js` read `document` at module scope, so the root would throw on import in Node and SSR while looking supported — a worse failure than an honest one. No `exports` map is added either; one with only a `"."` entry and no `"./*": "./*"` alongside would make every working subpath fail with `ERR_PACKAGE_PATH_NOT_EXPORTED`, which is the one change in this area that would genuinely break consumers. Shipping a root stub that throws a friendlier message was rejected too: it resolves, so a bundler would build clean and fail in the browser rather than at build time. `scripts/__tests__/assemble-npm-package.test.js` now fails if `main`, `module` or `exports` reappears, or if any root file reaches the tarball. Documentation caught up in the same pass: 14 MDX pages taught `import { X } from '@undrr/undrr-mangrove'` and now show the subpath with the binding the published bundle actually exports — which is not uniform, so `QuoteHighlight`, `UserFeedback`, `MegaMenu`, `ScrollContainer` and `ShareButtons` are default imports while most others are named. The React integration guide's component table is rebuilt from the built bundles and lists the exact import line per component, and `CookieConsentBanner`, `Snackbar` and `CodeBlock` are now stated to ship in no bundle at all rather than appearing importable. Checking the table against `dist/components/` also turned up the opposite error: `FullWidth.mdx` said its wrapper component "is not exported from `@undrr/undrr-mangrove`, so it is only available inside this repository", when it has had a webpack entry since [#847](https://github.com/unisdr/undrr-mangrove/pull/847) and the package has been publishing `components/FullWidth.js` the whole time — that page now gives the working import line. `docs/RELEASES.md` and `docs/ARCHITECTURE.md` follow, and `docs/RELEASES.md` no longer tells a releaser not to "fix" the dangling `main`. ([#1252](https://github.com/unisdr/undrr-mangrove/issues/1252))

- **The syndicated search widget's Drupal snippet hydrates:** its MDX told consumers to mark the container with `data-undrr-search-widget`, an attribute nothing in the library has ever queried, while the hydration selector is and always was `[data-mg-search-widget]`. Both the sentence and the copy-pasteable markup are corrected, along with the same spelling in the `CustomEndpoint` story's Drupal example, and no occurrence is left in the repo. Documentation only. ([#1255](https://github.com/unisdr/undrr-mangrove/issues/1255))

- **`QuoteHighlight` now sanitises its three HTML props, closing the divergence from `TextCta`:** `quote`, `attribution` and `attributionTitle` go through DOMPurify's default allow-list before they are rendered, which is the call `TextCta` already makes on its `text` prop and the cards and `Drawer` make on theirs. The difference was never a decision — [#1258](https://github.com/unisdr/undrr-mangrove/pull/1258) looked for a stated reason and found none — and of the three components documented there, this is the one whose content matches what `TextCta` sanitises: three short authored strings, hydration-fed from `data-quote`, `data-attribution` and `data-attribution-title` on a CMS-rendered container, so the values travel through markup rather than staying inside a consumer's wrapper. `Tab` and `MegaMenu` are deliberately not changed: `Tab`'s `data` is a whole panel body and a default pass would strip the `<iframe>` and embeds the prop exists to carry, and `MegaMenu`'s `bannerDescription` is injected as an entire `<article>` that consumers build in their own wrapper. **Consumer-visible:** the allow-list keeps everything these props are for — `<cite>`, `<em>`, `<br>`, and an anchor on an attribution name, each covered by a test — but markup that previously rendered is now filtered: `<script>`, event-handler attributes, `javascript:` URLs, and `<iframe>` and other embeds. Anyone putting panel-sized content through a pull quote will see it disappear. The one removal that is not an attack shape, and the one worth checking before you upgrade, is `target`: DOMPurify's default list drops `target` and `referrerpolicy`, so an attribution link authored as `target="_blank"` now opens in the same tab. That is the library-wide default and not a choice made for this component — `TextCta`, `Drawer` and the cards strip it from their HTML props too — and everything else an anchor carries (`href`, `rel`, `class`, `id`, `title`, `hreflang`, `lang`, `dir`, `aria-*`, `data-*`, including Linkit's `data-entity-*`) survives, so nothing goes unstyled and no entity reference is lost. Upstream sanitising is no longer required and is still worth keeping; the component's pass is a floor, not a replacement for a CMS output filter. The "you own sanitising this" wording #1258 added is reversed everywhere it was written — the component comment, the three render sites, the propTypes, the MDX section (now "Quote HTML handling"), the three CDN attribute rows and the AI manifest entry. The `<` check on `quote` stays and is now described for what it does: it picks the wrapper element, a `<p>` for a plain quote and a `<span>` for one with markup, and is no part of the safety. One knock-on worth knowing for anyone sanitising another component later: DOMPurify needs a DOM and the AI manifest renders components in plain Node, so the renderer now skips `QuoteHighlight` as it already skips `VerticalCard` and the rest, and its `renderedHtml` is curated in `scripts/ai-manifest/component-data.js` rather than auto-rendered — accurate today, and now something a markup change has to keep in step by hand. The manifest already has a guard for exactly that, `checkCuratedDrift`, which re-renders a curated component from `dist/` and compares its BEM classes; it cannot render a sanitising component either, and was swallowing that failure in an empty `catch`, so every curated entry belonging to a DOMPurify component looked covered and was not. It now reports each one as "could not verify" instead, which is how this gap became visible and is the only warning a reader has that the block is hand-maintained. The curated example also carries an `aria-label` on the `<section>` that React does not emit — the component gives the section no accessible name, which the curated-HTML a11y lint requires and which is a real limitation left for its own issue — so the example's published name and the hydration note both say the label is the consumer's to write and translate, rather than leaving that in a source comment nothing publishes. ([#1259](https://github.com/unisdr/undrr-mangrove/issues/1259))

- **New component — Segmented control, for a one-of-N view switcher:** the library had no segmented control, button group or toggle group, and each near-fit was wrong in a way consumers kept working around: Tabs look right but the ARIA tabs pattern expects a `tabpanel` per tab, which a view switcher has none of; Chips read as filters that combine; Radio is the correct semantics with no compact presentation, so teams invented the visual layer and drifted off Mangrove's button and focus-ring tokens. The risk-resilience-maps team reported it after shipping a `role="tablist"` with no panels ([#1188](https://github.com/unisdr/undrr-mangrove/issues/1188)). `.mg-segmented-control` is the presentation and nothing else: a `fieldset`, a `legend` and one `input[type=radio]` per segment, each followed by its own `label`, with the inputs clipped out of sight and the labels drawn from the button tokens. No JavaScript and no ARIA, so arrow-key navigation, the checked state, the "N of M" announcement, form submission and RTL traversal stay the browser's and stay correct. Vanilla HTML consumers can hand-author the markup; React consumers get `SegmentedControl` with `value`/`defaultValue`, `hideLegend`, `size` and `fullWidth`. Details in the component changelog. ([#1188](https://github.com/unisdr/undrr-mangrove/issues/1188))

- **Lint and format coverage now reaches the code the library ships:** ESLint's `files` patterns claimed story files and TypeScript and nothing else, so 205 component `.jsx` files — the shipped components and their tests — were walked past with `File ignored because no matching configuration was supplied`, and `src/` was passed to neither ESLint nor Prettier. `.jsx` is now claimed by the same rule set as the stories beside it, `src` is in `lint:js`, `lint:check` and the Prettier glob, and `yarn lint:coverage` (part of `lint:check`) fails when any source file matches no configuration, so an unlinted file in one of those directories cannot escape silently. Turning coverage on surfaced 74 problems; `prefer-const`, `eqeqeq`, `no-return-assign`, `no-console`, `func-names` and `no-bitwise` are now clean, with four React ref callbacks rewritten to statement bodies so they stop returning the element they assign. React 19.3 does not reject that return value — it stores it as the ref cleanup and, finding it is not a function, still calls `ref(null)` on detach — so the four sites behaved correctly; returning a _function_ from a ref callback is the shape that would silently replace the detach, and the statement bodies keep these four out of reach of it. `react/no-danger` is enabled at warning severity over a 22-site backlog that needs a per-site audit — the rule only inspects lowercase DOM elements, so the real figure is the 36 non-test `dangerouslySetInnerHTML` sites in the tree, and a clean rule run is necessary rather than sufficient — and `react/no-array-index-key` (51 sites) stays off; both decisions are recorded in `eslint.config.mjs`. Of the 13 suppression comments that became live, five were misplaced — they sat a line above the violation and suppressed nothing — and are now attached to the right line; four named rules that stay off and have become plain comments keeping their explanation. Unused directives are reported as errors rather than warnings, so a stale suppression fails the build. ([#1235](https://github.com/unisdr/undrr-mangrove/issues/1235), [#1241](https://github.com/unisdr/undrr-mangrove/issues/1241), [PR #1247](https://github.com/unisdr/undrr-mangrove/pull/1247))

- **The repository's package root exports resolve again, and are now tested.** `src/index.js` — the file this repo's `package.json` names as `main` and as the `.` entry in `exports` — had two broken re-exports. `IconCard` was re-exported as a default that `IconCard.jsx` does not have, so the binding was `undefined` and rendering it threw `Element type is invalid`; it now uses the named form, matching the component and its hydration barrel. `CookieConsentBanner` was re-exported from a directory with no index file, which does not fail one binding but the whole module: importing anything from the entry point raised `Cannot find module`. That one had been broken since the component landed in June 2025. Neither had anything checking it, so a new test imports the entry point and asserts that no export is `undefined`. Hydration through `*.hydrate.js` was never affected. **This is not yet a consumer-visible fix.** The published npm tarball is assembled by `scripts/assemble-npm-package.mjs`, which ships neither `src/` nor `dist/` and writes a `package.json` with `main: "dist/index.js"` and no `exports` field, so on every published version to date — including `1.8.2` (`latest`) and `2.0.0-rc.2` (`next`) — `import … from '@undrr/undrr-mangrove'` fails with `ERR_MODULE_NOT_FOUND` before any of these bindings is reached. Consumers of the package import the per-component subpaths (`@undrr/undrr-mangrove/components/IconCard.js`) instead. Making the package root resolve for them is a separate packaging fix. ([#1240](https://github.com/unisdr/undrr-mangrove/issues/1240), [PR #1247](https://github.com/unisdr/undrr-mangrove/pull/1247))

- **Three components that render caller HTML now say so:** `MegaMenu` (`bannerDescription`, at the desktop banner, the no-items call-to-action panel and the mobile sidebar), `Tab` (a tab object's `data`) and `QuoteHighlight` (`quote`, `attribution`, `attributionTitle`) all render caller-supplied markup with `dangerouslySetInnerHTML` and none of them sanitises it. That is unchanged — this is documentation only, with no rendering change and no sanitisation added. Each now carries a block comment stating the contract, a pointer at every render site, prop documentation, a named section in its MDX placed where a consumer configuring that prop arrives, and a line in its AI manifest entry. The reason for writing it down is that the repo has a convention these three sit outside of: `dompurify` is a direct dependency and `VerticalCard`, `HorizontalCard`, `HorizontalBookCard`, `IconCard`, `StatsCardItem`, `Drawer` and `TextCta` all sanitise internally, so a reader who knows that code reads these sites as an oversight rather than a decision. State it accurately: these are caller-supplied props, so the trust boundary is the consuming application's own code — a CMS output filter in most integrations — not a network response, which is what makes them a weaker case than [#1254](https://github.com/unisdr/undrr-mangrove/pull/1254). They are undocumented contracts, not vulnerabilities. Two things found while writing it: `Sidebar.jsx` already pointed at "the same caller-sanitised HTML contract as the existing desktop banner", which had never been written down anywhere, and `Tab`'s second `dangerouslySetInnerHTML` is a fixed string literal (an HTML comment JSX cannot otherwise emit) rather than caller input, now labelled as such so an audit does not have to work that out twice. `QuoteHighlight`'s manifest hydration note had carried the contract correctly for some time and was the only place it appeared. Superseded for `QuoteHighlight`, which now sanitises — see the entry above; the `MegaMenu` and `Tab` contracts stand as written. ([PR #1258](https://github.com/unisdr/undrr-mangrove/pull/1258))

- **The half-scrollbar overhang on full-bleed components is documented, not fixed in the library:** every full-bleed escape Mangrove ships (`mg-hero`, `mg-hub-header`, `mg-on-this-page-nav`, `mg-container-full-width`) sizes itself with `100vw`. `vw` counts the classic vertical scrollbar and the containing block does not, so on any page that scrolls vertically each escape overhangs by half a scrollbar on both sides and the page picks up about 8px of horizontal scroll, in both directions, on every variant. Nothing inside a component can measure the scrollbar; only the page root can absorb it, with `overflow-x: clip` on both `html` and `body`. That rule is **not** shipped. It ends the sideways scroll by making anything wider than the page unreachable — no scrollbar, and `scrollIntoView()` cannot pan to it either — and the library cannot see what a consuming site renders. On the UNDRR platform specifically, Drupal's `views-view-table.html.twig` emits `<div class="table-responsive">` and no UNDRR theme styles that class, so wide Views tables are read today by scrolling the page sideways; shipping the clip would have cut that content off on nine sites. The rule, the reasoning and its cost are now written up under [page-level setup](https://mangrove.undrr.org/?path=/docs/components-fullwidth--docs#page-level-setup) for a site to adopt deliberately, with pointers from the Hero docs and from Best practices. Includes why both `html` and `body` are load-bearing (either alone leaves the overflow entirely intact), why it must be `clip` and never `hidden` (`hidden` makes the page a scroll container and detaches `position: sticky`), and that Safari below 16 keeps today's behaviour. See [#1203](https://github.com/unisdr/undrr-mangrove/issues/1203).

- **The AI manifest counts its global custom-property groups instead of stating a number:** `llms.txt` generated its list of global `--mg-*` groups from `GLOBAL_PREFIXES` but introduced it with a hand-typed "Four groups", so adding a group left the document claiming four and listing five. The count is now derived from the same data as the list, and `tokens.json`'s `scope.excludes` and `docs/AI-MCP-INTEGRATION.md` say "every group" rather than "all four". No group changed, so every generated document is byte-identical. ([#1203](https://github.com/unisdr/undrr-mangrove/issues/1203))

- **The syndication search widget's endpoint trust contract is now written down:** `SyndicationSearchWidget` renders the search response as HTML at three sites in `ResultItem.jsx` and sanitises none of it, because Elasticsearch wraps matched terms in `<em>` and escaping the response would print those tags instead of emphasising the match. That is the right call and it is unchanged here — this is a documentation-only note, with no rendering change and no sanitisation added. It is worth recording because `searchEndpoint` is consumer-configurable, through the config prop and through `data-search-endpoint`, so pointing it at a different service means rendering that service's HTML unfiltered; and because a syndication widget renders into partner domains rather than only UNDRR's. The three sites now carry the reasoning, the component MDX documents the contract next to the endpoint configuration, and the AI manifest entry states it for agents wiring the widget up from the manifest alone. Scope note for anyone reading the `react/no-danger` backlog in `eslint.config.mjs`: this closes the ResultItem part of that audit in prose, not by adding suppressions — the rule is off on `main` today, and these sites keep plain comments so nothing goes stale either way. ([PR #1254](https://github.com/unisdr/undrr-mangrove/pull/1254))

- **The manifest states each component's lifecycle instead of implying it:** `index.json` distinguished `vanillaHtml`, `vanillaModule` and `hydration`, but `vanillaModule` was only emitted when there was one. "Vanilla HTML with no lifecycle module" and "vanilla HTML plus a module" were therefore the same entry, and the only way to tell them apart was to fetch `/js/{guess}.js` and see whether it 404'd. `vanillaModule` is now a boolean on every component, `vanillaScripts` lists the files to load when it is true (each one the `file` of a `library.vanillaScripts` entry), and the detail file carries either the full contract or `false` plus an optional `vanillaModuleNote` saying why there is none. Reported by the `undrr-risk-resilience-maps` team ([#1197](https://github.com/unisdr/undrr-mangrove/issues/1197)).

- **`yarn validate-manifest` checks the lifecycle claim against the files on disk:** a `hydration` or `vanillaModule` contract naming a module under `js/` now fails the build unless `stories/assets/js/{name}.js` exists, so the manifest cannot advertise a URL that 404s or survive a rename. The `VANILLA_SCRIPTS` catalogue is checked in both directions: every entry must name a real file, and every module that ships must be listed. The second half caught `js/copy-button.js`, which shipped and was named by a component contract but was missing from the list; `js/drawer.js` and `js/table-of-contents.js` are listed too. A component cannot carry both a `vanillaModule` contract and a `vanillaModuleNote` explaining that it has none. The check reads the source tree, so it runs the same with or without a build, and `vanillaModules(name)` in `component-data.js` now builds the module URLs the way `hydrationModules(name)` already did, which is what makes a claim resolvable back to a file ([#1197](https://github.com/unisdr/undrr-mangrove/issues/1197)).

- **Browser-driven checks of the cookie consent bar need `hideFromBots: false`:** vanilla-cookieconsent's `hideFromBots` option defaults to `true`, and the UNDRR CDN configuration leaves it that way. When it is on and `navigator.webdriver` is `true` — any Playwright, Puppeteer, Selenium or CDP-driven session — the library returns from `run()` before creating a single node, while still reporting success: `window.CookieConsent` is a populated object and the CDN configuration script logs `Cookie banner initialized successfully`. This is why the bar was reported as never rendering in Storybook when it renders for a person, and it affects anything automated that expects to see it, not just the `CookieConsentBanner` stories. See [#1202](https://github.com/unisdr/undrr-mangrove/issues/1202), [#1242](https://github.com/unisdr/undrr-mangrove/pull/1242), and the component's "Rendering check" story for the pattern that asserts the bar for real.

- **Show more target lookups are ordered, and the #1222 reasoning is corrected:** `show-more.js` resolved its target with `document.querySelector`, so two toggles left on the default `.mg-show-more--container` both drove the first block on the page. It now climbs the toggle's ancestors and takes the first match inside one, falling back to the document if the walk reaches `<html>` without matching. The #1222 note above said there was "no container to scope to" because revealed content need not be a sibling or descendant of its toggle. The premise holds and the conclusion did not follow: it rules out _confining_ the lookup, not _ordering_ it, and an ancestor walk is never worse than the document-wide one — it is the same answer whenever the target is genuinely elsewhere, and the right one whenever two toggles share a selector. That note now says scoping was judged out of scope for the sweep rather than impossible. The React `ShowMore` wrapper needed a different fix: its items are flat siblings, so the walk cannot separate two that share a `collapsable_wrapper_class`; each item now carries a minted id and its toggle targets that. Detail in the ShowMore changelog. ([#1238](https://github.com/unisdr/undrr-mangrove/pull/1238), [#1228](https://github.com/unisdr/undrr-mangrove/issues/1228))
- **Curated component descriptions now reach the AI manifest:** `getDescription()` resolved the component's own docblock ahead of the curated `description` in `scripts/ai-manifest/component-data.js`, so guidance written for the manifest never reached `index.json` — the file an agent greps first. An agent searching the index for "icon button" found nothing, even after [#1225](https://github.com/unisdr/undrr-mangrove/pull/1225) wrote the two icon-only classes into the Buttons entry. The curated description now wins everywhere, which also retires the narrower `patterns-*` exception added for [#1129](https://github.com/unisdr/undrr-mangrove/issues/1129). `summary` and `description` are no longer the same string: component entries take an optional one-sentence `summary` for the index listing, required once the description runs past 200 characters and enforced by `yarn validate-manifest` and by `scripts/__tests__/component-data.test.js`. 37 descriptions and 50 summaries changed; the descriptions that lost useful docblock detail (the `crop="autocrop"` warning on Logos, the accepted icon name formats, the Cloudflare static templates on the error pages, and four more) had it folded into the curated text. Auto-rendered HTML examples are also named after the component instead of carrying the whole curated description as their `name`. ([#1237](https://github.com/unisdr/undrr-mangrove/pull/1237))
- **`yarn lint` no longer deletes `eslint-disable` comments:** ESLint's flat config defaults `linterOptions.reportUnusedDisableDirectives` to `warn`, and `--fix` acts on that warning, so `yarn lint:js` silently removed any suppression naming a rule the config does not enable — leaving trailing whitespace that `yarn prettier:check` rejected while `yarn lint:check` still exited 0. All 15 `eslint-disable` comments in the repo name rules `eslint.config.mjs` does not enable, and several of those rules it turns off on purpose, so enabling rules one by one was not the fix. Only two of the 15 were ever at risk, because the other 13 sit in `.jsx` files ESLint currently skips entirely ([#1235](https://github.com/unisdr/undrr-mangrove/issues/1235)) — they become live the day that coverage lands. `lint:js` now passes `--fix-type problem,suggestion,layout`, which omits `directive`, and `lint:check` drops `--quiet` so a genuinely stale directive is reported instead of deleted. `no-control-regex` is enabled, which makes the one suppression in a linted file real. A new `scripts/__tests__/lint-scripts.test.js` holds that wiring, and CI now runs `yarn lint`, `yarn prettier:check` and `git diff --exit-code` together so the fixing command can never again produce a tree the format check rejects. ([#1232](https://github.com/unisdr/undrr-mangrove/pull/1232))
- **Breaking — the four CamelCase SCSS aliases removed:** `ShowMore.scss`, `FullWidth.scss`, `TableOfContents.scss` and `SyndicationSearchWidget.scss` each existed only to `@import` their kebab-case sibling and `@warn` that they were deprecated. All four are deleted, so the npm package no longer ships `scss/Utilities/ShowMore/ShowMore.scss`, `scss/Utilities/FullWidth/FullWidth.scss`, `scss/Components/TableOfContents/TableOfContents.scss` or `scss/Components/SyndicationSearchWidget/SyndicationSearchWidget.scss`. Nothing in the library imported them (`stories/assets/scss/_components.scss` already imports the kebab-case files); they shipped only because the package assembly copies every `stories/**/*.scss`. Consumers importing a CamelCase path switch to the kebab-case one — `show-more`, `full-width`, `table-of-contents`, `syndication-search-widget` — which is the same stylesheet the alias forwarded to, so the compiled CSS is unchanged. Dropping one and keeping three would give consumers a break they could not generalise from, and a major release is the moment to take all four. Migration table in [the 2.0 release notes](https://mangrove.undrr.org/?path=/docs/getting-started-release-notes-v2-0--docs). ([#1193](https://github.com/unisdr/undrr-mangrove/pull/1193))

The six named statuses are solid `CanvasText` shapes that survive a missing ring on their own, and are explicitly left without it. Normal rendering is unchanged at every ring width — the rule is inside the `@media (forced-colors: active)` block — and no token changed, so none of the component's fourteen custom properties behaves differently. - **Hydration lookups are scoped to the element being hydrated:** a sweep of all sixteen `*.fromElement.js` files and their `*.hydrate.js` barrels for lookups that reach past the container they are given ([#1205](https://github.com/unisdr/undrr-mangrove/issues/1205)). The barrels are re-exports and hold no lookups. ScrollContainer's `doc.querySelector('.mg-scroll__content')` turned out not to be the document: `doc` is a throwaway document the same function builds from `container.innerHTML`, so two hydrated containers on a page never read each other's children and the reported symptom does not reproduce. It was still wider than the container being hydrated — a wrapper belonging to a nested scroll container matched — and now reads the live container, with the `DOMParser` round trip gone. The real wrong-instance lookup was in the syndicated search widget's pager, which scrolled to the first `[data-mg-search-widget]` on the page rather than the widget the reader had just paged. Per-component detail is in the ScrollContainer and Syndicated search changelogs. ([#1222](https://github.com/unisdr/undrr-mangrove/pull/1222))
- **The syndicated search filter drawer mirrors in Arabic:** the mobile filter drawer was the one direction-specific declaration [#1192](https://github.com/unisdr/undrr-mangrove/pull/1192) left alone, because `left: 0` could not be swapped on its own: the panel's entry is a `translateX` keyframe, which travels on a physical axis, so `inset-inline-start` would have moved the resting edge to the right in Arabic while the panel still slid in from the left, and the shadow would still have pointed away from the page. - **Four documentation claims corrected, and the ΔE method written down:** each of these stated something untrue, and all four were verified against the source before being changed. `docs/REVIEW-CHECKLIST.md` justified the no-`role="list"` house rule by saying `jsx-a11y/no-redundant-roles` flags the attribute; that rule does not exist in this repo — `eslint.config.mjs` never registers the `jsx-a11y` plugin, every `jsx-a11y/*` rule it names is `off`, and `no-redundant-roles` is absent entirely. The rule itself stands, so only the reason is replaced: the `mg-list-unmarked` mixin keeps the implicit `list` role, which makes the attribute redundant. `_tokens-data-viz.scss` and StatusLabel's MDX disagreed about the categorical palette's worst pair at seven series — ΔE 3.2 against 2.2. - **Hydration never mounts a component into its own output:** `createHydrator` skips a selector match that sits inside an already-hydrated container the same selector also matches. A component is free to render the same `data-mg-*` marker its hydration selector matches — `SyndicationSearchWidget` renders `data-mg-search-widget` on its root so its pager can find the widget to scroll to — and until now a `hydrator.update()` re-scan treated that React-rendered marker as an un-hydrated target and mounted a second widget inside the first, nesting three deep. `update()` is the documented way to hydrate markup added after the first pass, so every consumer calling it duplicated every syndicated search widget on the page. The check is on the ancestor matching the same selector, not on it merely being hydrated: `ScrollContainer` and `Drawer` read the consumer's markup in their `fromElement` and re-emit it through `dangerouslySetInnerHTML`, so a different component's hydration host nested inside one — a scrolling row of hydrated cards, which is `ScrollContainer`'s canonical use, or an author-entered card in a Drupal drawer — comes back out of React verbatim and still hydrates. The walk reads the DOM rather than one hydrator's own bookkeeping, so a page that builds two hydrators for one selector is covered too. Markup added outside a hydrated container hydrates as before; appending into or refilling a hydrated container is a no-op, and the way to replace its contents is `unmountAll()` then `update()`. The rules are stated in [`docs/HYDRATION.md`](https://github.com/unisdr/undrr-mangrove/blob/main/docs/HYDRATION.md) and the authoring guide so a new component does not reintroduce it ([#1234](https://github.com/unisdr/undrr-mangrove/pull/1234), [#1227](https://github.com/unisdr/undrr-mangrove/issues/1227)).

- **The vanilla JS modules ship as source, and the docs now say so:** `stories/assets/js/README.md` described a UMD bundle at `dist/js/{name}.min.js` as the build's output for every module in that directory, and `docs/ARCHITECTURE.md` described webpack's first config as producing `dist/js/*.min.js` and `dist/css/`. No such file has ever been emitted: the entry glob in `webpack.entries.js` interpolated `/stories/assets/**/*.js` into `./stories${suggestFiles}`, so it globbed `./stories/stories/assets/**/*.js`, matched nothing, and handed webpack an empty entry object. Nothing consumes a minified variant — the CDN and the npm `js/` directory both serve the verbatim copies CopyPlugin makes at `dist/assets/js/*.js`, which is also why [#1191](https://github.com/unisdr/undrr-mangrove/pull/1191) had already corrected a CopyButton snippet that pointed at `dist/js/copy-button.min.js`. The documentation is corrected rather than the glob: emitting the bundles would have added nine UMD files nobody loads to every CDN release, and fixing the glob as written would also have swept in the four `stories/assets/js/__tests__/` specs and the five Node-only SCSS token tests under `stories/assets/scss/__tests__/`, the same class of leak as [#1218](https://github.com/unisdr/undrr-mangrove/issues/1218). `webpack.entries.js` is deleted — its CSS branch had no caller either, because `yarn scss` compiles the stylesheets before webpack runs — and the first config now declares an empty entry with a note that it exists for its CopyPlugin patterns, and loses the `[name].min.js` filename and UMD library target that described the bundle it never emitted. `dist/` is unchanged: a build before and a build after produce 260 identical files, the only difference being the per-build `Compiled on:` timestamp each component bundle carries, which differs between any two builds. That config's `optimization.minimizer` list is load-bearing despite the empty entry, and now says so at length: webpack 5's default list minifies JS, CSS **and** HTML, so replacing it with `CssMinimizerPlugin` alone is what keeps `dist/assets/js/*.js` byte for byte what a contributor wrote, keeps the error pages readable, and keeps the CSS header comment. Deleting it would silently start minifying the JS and HTML the CDN serves. ([#1253](https://github.com/unisdr/undrr-mangrove/issues/1253))

- **The AI manifest publishes imports that resolve:** every `import` line in `ai-components/index.json` and the per-component detail files named the package root — `import { IconCard } from "@undrr/undrr-mangrove"` — which does not resolve on any published version. The generator read `src/index.js` and treated its exports as the consumer surface, but the tarball ships neither `src/` nor `dist/`, so an agent following the manifest wrote an import that throws `ERR_MODULE_NOT_FOUND`. It now reads the export names out of the built bundles in `dist/components/`, which is what the package publishes under `components/`, and emits the subpath — `import { IconCard } from "@undrr/undrr-mangrove/components/IconCard.js"` — with a named or default binding to match what the bundle actually exports. 49 components carry an import line, up from the 22 the root export list produced, and 47 of them resolve and bind when checked against a freshly packed tarball; the other two are `ShowMore` and `Tab`, whose bundles read `document` as they load — both import a vanilla module that self-initialises on `DOMContentLoaded` — so they need a browser rather than a resolver. Those two keep their import line, which is correct in a browser and through a bundler, and carry `importRequiresDom: true` in the index with a note in the detail file saying what to do on a server-rendered page: an agent that would otherwise meet `document is not defined` and have nothing in the manifest to explain it now knows before it runs the line. The flag is set by importing every bundle at generation time rather than by guessing from its source, and a missing or stale `dist/components/` is now a hard failure instead of a manifest that quietly loses every import line. A component that ships in no bundle still carries no import line at all instead of an unusable one. `docs/COMPONENT-GUIDE.md`, `docs/ARCHITECTURE.md` and `docs/REVIEW-CHECKLIST.md` no longer present `src/index.js` as the way to publish a component: a webpack entry is, and the entry point export is the repository's own. Whether the package root should be a supported entry point at all is still open on [#1252](https://github.com/unisdr/undrr-mangrove/issues/1252), and nothing about the published shape changes here — a new test packs the assembled package and records it, including that `main` names a file the tarball does not contain. ([#1252](https://github.com/unisdr/undrr-mangrove/issues/1252))

## 1.8.0 — 2026-06-19

See the [GitHub Release](https://github.com/unisdr/undrr-mangrove/releases/tag/v1.8.0) for full details.

### Security

- **Dependency update cooldown.** Renovate now waits until a release is at least 7 days old before it proposes the update (`minimumReleaseAge: "7 days"` with `internalChecksFilter: "strict"`), so a compromised package version that gets detected and unpublished within its first days never reaches a pull request here. Security advisories (`vulnerabilityAlerts`) are exempt, so genuine fixes are not delayed. Dependabot is retired and Renovate is now the sole dependency bot, which also ends the duplicate update PRs. A separate spike tracks evaluating pnpm for its scripts-off-by-default behaviour (#1038). (#1039)

### Removed

- **D3 chart components, `MapComponent`, and `Fetcher` removed.** The npm exports `BarChart`, `MapComponent`, and `Fetcher` are no longer published. The internal-only Storybook stories `Histogram`, `IndexChart`, and `ConnectedScatterplot` are also removed. D3 and Leaflet packages are dropped from the dependency tree. Migrate charting to [Recharts](https://recharts.org/), mapping to [MAPX](https://mapx.org/), and data loading to [react-query](https://tanstack.com/query) / [SWR](https://swr.vercel.app/) or server-side load. ([#1011](https://github.com/unisdr/undrr-mangrove/issues/1011))

## 1.7.0 — 2026-05-11

See the [GitHub Release](https://github.com/unisdr/undrr-mangrove/releases/tag/v1.7.0) for full details.

### Runtime

- **Node.js 22 is now the declared minimum** (Node 20 reached EOL on 2026-04-30). `engines.node` set to `>=22.0.0`. CI and Docker continue to run Node 24. `.nvmrc` added so `nvm use` picks the CI-pinned version. (#1003)

### Build & tooling

- TypeScript 5 → 6, ESLint 9 → 10 majors (#977).
- React 19.2.5 → 19.2.6 (#991).
- Yarn 4.14.1 (#952).
- Batch dep updates: `jest` 30.4.x monorepo (#997), `typescript-eslint` 8.59.2 (#993), `@babel/preset-env` 7.29.5 (#961), `stylelint` ~17.11.0 (#937), `globals` 17.6.0 (#964), `sass-loader` 16.0.8 (#990), plus batched minor/patch (#960, #984).

### Security

- Patched 17 Dependabot security alerts via yarn resolutions (#978).
- Patched `brace-expansion` ReDoS via resolution (#979).

### Code quality

- New `react-doctor` component-quality linter codified as a project convention. Health score moved 57 → 68 across the sweep, with 66 of the original 398 findings cleared. (#985, #987, #988, #989, #996.)
- House conventions for component authors documented in `docs/AI-CODING-AGENTS.md`: no em-dashes or three-period ellipses in JSX text; prefer `use()` over `useContext()` on React 19+; hoist default `[]` / `{}` props to module-level constants; no inline render helpers (extract as named subcomponents); lazy `useState` init; effect cleanup discipline; per-call-site triage for `dangerouslySetInnerHTML` (inline DOMPurify vs documented caller contract). (#992)
- React Doctor health badge added to `README.md` and the Storybook _Introduction_ page. The badge is a manually-refreshed periodic snapshot — see `docs/AI-CODING-AGENTS.md#refreshing-the-score-badge`. (#992, #996.)
- **Consumer-visible API note:** `Component.defaultProps` has been removed from `FooterIcons`, `FooterConditions`, `FooterConditions2`, `FooterLists`, `Link`, and `ScrollContainer`. React 19 deprecates `defaultProps` on function components; the defaults are now declared via destructured parameters, so component behaviour is unchanged. Only consumers that read `Component.defaultProps` for introspection (rare) need to adjust. (#985, #988)
- `useContext(SearchContext)` swapped to React 19's `use(SearchContext)` in `SyndicationSearchWidget` (#988). Internal change; identical behaviour at top-level call sites.

### Documentation

- `docs/AI-CODING-AGENTS.md` extended with the _Component quality checks with react-doctor_ section (above), linked from `CONTRIBUTING.md`, `docs/DEVELOPMENT.md`, and `docs/REVIEW-CHECKLIST.md`. (#992)
- Tracking issue [#986](https://github.com/unisdr/undrr-mangrove/issues/986) documents the remaining `react-doctor` work, organised into risk buckets for future sweeps.

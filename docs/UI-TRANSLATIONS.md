# UI translations

Mangrove components with built-in label catalogues select their interface copy
at runtime through `lang`. Consumers can override individual labels without
copying a complete translation catalogue. The same selection works in React
and in the components' React hydration adapters.

## Supported components and languages

The runtime catalogue contract covers CopyButton, ShareButtons, ServiceNotice,
Snackbar, Drawer, Gallery, ScrollContainer, Tab, MegaMenu, OnThisPageNav and
SyndicationSearchWidget, together with UserFeedback.

Publication remains component-specific. Snackbar has no standalone published
webpack bundle, and OnThisPageNav's React wrapper is used by Storybook; its
production integration is the vanilla module. Their source components use the
shared catalogue contract, but this does not introduce new npm/CDN entry points
or React hydration adapters for them.

The catalogues provide English (`en`), Arabic (`ar`), Spanish (`es`), French
(`fr`), Japanese (`ja`), Russian (`ru`) and Simplified Chinese (`zh`). Selection
uses the primary language subtag, ignoring surrounding whitespace and case:
`fr-CA` and `fr_CA` select French. Chinese regional or script subtags currently
select the same Simplified Chinese catalogue; there is no separate Traditional
Chinese translation.

These catalogues cover component controls and status messages. Applications
still supply translated content such as gallery captions, navigation items,
drawer titles, notification messages and search result content. Selecting the
search widget's interface language does not change its query, content-language
filters, taxonomy data or date-formatting configuration.

This work adopts existing catalogues rather than claiming a complete string
audit. Remaining uncatalogued text includes Gallery's thumbnail control names,
Snackbar's severity announcement prefix, ShareButtons' failure alerts, and
controls generated by separate vanilla modules. These need further catalogue
and translation work; switching `lang` does not translate them.

## React usage and precedence

Pass `lang` explicitly when rendering a component. The component does not read
the browser's document language during render, so server and client rendering
can use the same inputs.

```jsx
import { CopyButton } from '@undrr/undrr-mangrove/components/CopyButton.js';

<CopyButton
  lang="fr-CA"
  textToCopy="https://example.org/"
  labels={{ tooltipLabel: 'Lien copié' }}
/>
```

Label precedence, from lowest to highest, is:

1. English defaults.
2. The selected built-in catalogue.
3. The consumer's `labels` overrides.
4. Existing dedicated label props, where the component provides them.

For example, CopyButton's `ariaLabel`, `copiedLabel` and `tooltipLabel` and
ServiceNotice's `retryLabel` and `statusUrlLabel` retain their precedence over
the corresponding `labels` keys. Omit an override to use the catalogue value.
Follow each component's label types; the search widget also supports
function-valued labels for plural-sensitive messages.

ScrollContainer's `ariaLabel` identifies the content of the row and overrides
`labels.ariaLabel`. Its translated `labels.navigationLabel` template inserts
that name at `{label}`; override the template to customize the complete
navigation name. Without either override, both parts come from the catalogue.

Omitting `lang` selects English labels and leaves HTML language and direction
inheritance intact. A surrounding HTML `lang` alone does not select labels for
a directly rendered React component. Pass the same language to the component.
Changing `lang` on rerender changes its built-in labels while retaining explicit
overrides.

## Language metadata and direction

The original `lang` value is retained in the rendered HTML; catalogue selection
does not rewrite `fr-CA` to `fr`. A supplied supported language selects `rtl`
for Arabic and `ltr` for the other built-in languages. An explicit `dir` takes
precedence.

Unsupported languages use English defaults for missing labels while preserving
their original HTML language metadata. They do not force a direction: a custom
Hebrew translation can use `lang="he"`, its own `labels`, and inherited or
explicit `dir="rtl"`. Empty language boundaries also remain meaningful: they
stop HTML language inheritance and do not silently select an ancestor's language.

This separation matters for mixed-language pages and Arabic font routing.
Keep language and direction on each rendered language boundary, including
detached dialogs and portal contents that cannot inherit from the component's
main DOM root. See the [accessibility guide](ACCESSIBILITY.md) for broader
language and direction requirements.

## HTML and React hydration

For components with a `fromElement` adapter, language selection uses:

1. The hydration container's `data-lang`, if present.
2. The nearest HTML `lang`, including the container itself.
3. English labels when neither is supplied.

A valid `dir="ltr"`, `dir="rtl"` or `dir="auto"` on the hydration container is
forwarded as an explicit direction override. Ancestor direction is not copied
into a prop: a local supported `data-lang` can establish its own direction,
while unsupported languages retain normal DOM inheritance. There is no
`data-dir` option.

```html
<section lang="fr">
  <div data-mg-copy-button data-text-to-copy="https://example.org/">
    <button type="button">Copier le lien</button>
  </div>
  <div
    data-mg-copy-button
    data-lang="es"
    data-text-to-copy="https://example.org/"
    data-tooltip-label="Enlace copiado"
  >
    <button type="button">Copiar el enlace</button>
  </div>
</section>
```

Load and invoke the component's hydration module as described in its own guide.
Existing dedicated label attributes and supported `data-labels` objects remain
overrides. Do not inject English labels merely because an attribute is absent:
that would hide the selected catalogue. Read language from the actual container
and its ancestors, not the global document, so nested boundaries and separate
documents work correctly.

HTML language attributes do not translate static markup by themselves. The
server must render appropriate initial text and accessible names. Separate
vanilla JavaScript modules retain their own documented contracts. In particular,
OnThisPageNav's React catalogue support does not replace its plain HTML
`data-mg-on-this-page-nav-label` or authored `aria-label`; Tab's vanilla enhancer
does not translate authored tab content. Do not infer automatic translation for
every `data-mg-*` component from the React hydration contract.

Search widget built-in Russian plural functions run when `lang` selects the
bundled catalogue, including through hydration. Custom function-valued overrides
must be supplied from JavaScript; JSON `data-labels` can carry strings only.

## Adding or maintaining a catalogue

Use the pure helpers in `src/i18n.js`: `createLabelResolver` merges a component's
defaults, selected catalogue and overrides; `getLanguageProps` keeps HTML
language and direction consistent; `languageFromElement` reads hydration
language boundaries. Keep translations with their owning component, normally in
`_labels.js`, rather than importing stories or introducing a global catalogue
that pulls every component's translations into each bundle. UserFeedback keeps
its established `UserFeedback.labels.js` filename.

Keep existing English default and label exports compatible when moving them
out of JSX. Re-export public resolvers through the component's actual webpack
entry or hydration barrel: an export in `src/index.js` alone does not publish a
package API. New labels need English defaults, translated entries, PropTypes and
documentation. Preserve placeholder names and any function-valued labels when
merging; never serialize a catalogue to clone it. Existing draft translations,
including ServiceNotice's, still need native-speaker review before being treated
as editorially approved.

Storybook's locale toolbar should supply `lang` to the runtime component while
preserving explicit story args and label overrides. Content examples may have
their own translated fixtures. A decorator that supplies a complete label object
can conceal a broken runtime resolver or overwrite a story's custom copy.

For a new component, decide which text belongs to the interface and which is
consumer content. Follow this contract when adding a built-in UI catalogue; a
component that only displays supplied editorial content need not gain one.

### Creating a component with interface labels

Keep the catalogue independent of JSX, so its resolver can also be imported
without React or a browser. For example, a component-local `_labels.js` can
export its defaults and resolver using the shared helper:

```js
import { createLabelResolver } from '../../../src/i18n';

export const DEFAULT_EXAMPLE_LABELS = { closeLabel: 'Close' };
const LABELS_FR = { closeLabel: 'Fermer' };
// Abbreviated example: add each supported language's own catalogue here.
export const getExampleLabels = createLabelResolver(DEFAULT_EXAMPLE_LABELS, {
  en: DEFAULT_EXAMPLE_LABELS,
  fr: LABELS_FR,
});
```

The component resolves `getExampleLabels(lang, labels)` during render and spreads
`getLanguageProps(lang, dir)` onto its root and any detached language boundaries.
Declare `lang`, `dir` and the individual label keys in PropTypes. Its hydration
adapter forwards `languageFromElement(container)` and optional
`labelsFromElement(container)`; dedicated label attributes override those JSON
values only when present. The published entry re-exports the resolver. Use
CopyButton or UserFeedback as the complete reference, and
`.storybook/withLanguage.jsx` for locale-aware stories.

### Maintaining translations

When adding a key, update the English default and each supported catalogue in
the same change, retaining placeholder names and value types. Partial
catalogues intentionally use English fallback; record missing translations
rather than silently treating fallback copy as approved translation. Check the
rendered control or message, including its accessible name and plural forms.
When adding a language, also review the supported-language documentation,
`src/i18n.js` direction mapping and Storybook locale mapping. Adding a catalogue
does not automatically add a locale toolbar option.

## Verification

Test observable behaviour at the boundaries:

- Supported languages, regional tags, missing language, unsupported language,
  partial overrides, and switching language after rendering.
- Arabic direction, explicit direction overrides, and unsupported custom
  language metadata without an unwanted `ltr` boundary.
- Hydration precedence for `data-lang`, self/ancestor `lang`, nested and empty
  language boundaries, and existing label attributes.
- Labels inside dialogs, nested components and external portals; search plural
  functions and token interpolation must survive the merge.
- Server rendering without browser globals for components that already support
  it. Pure translation helpers must also work without a DOM; this does not make
  an otherwise browser-only component server-renderable.
- The locale toolbar, long translated labels, RTL layout and accessible names.

Update component MDX, hydration attributes in the AI manifest and any examples
alongside the implementation. Follow the [review checklist](REVIEW-CHECKLIST.md)
and run the build and manifest validation to check the published contract.
